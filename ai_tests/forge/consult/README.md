# consult の consult brief の確認

## 目的

review から委譲された consult が、各 consult topic について、次を満たすかを確かめる。

1. consult topic の直前に、consult brief（要旨と推奨案）を作り終えてから、利用者に話しかける
2. consult brief が、要旨と推奨案の 2 欄で、合わせて 10 行程度である
3. consult brief の要旨と推奨案が、consult topic ごとの独立した値として、JSON に記録される
4. 記録に失敗したとき、失敗が利用者に伝わり、既定値で補われず、consult brief の提示が続く

判定は AI の振る舞いに依存して揺れ、費用もかかるため、CI のゲートの対象外とし、手動で実行する。

## 手順

1. 所見が出やすい実在の書類を対象に、`/forge:review --interactive --files <対象>` を実行する
2. consult が提示を始めたら、利用者として採否に応答する
3. consult の提示の前後で、次を確かめる
   - consult が、利用者に話しかける前に、調査と記録を終えているか（動作記録で、記録の script の実行が、利用者向けの出力より前にあるか）
   - consult brief の行数と、2 欄であるか
   - 評価 JSON と同じディレクトリに `consult_brief_{通し番号}.json` が作られ、`review_id`・`round_number`・`sequence`・`finding_ids`・`summary`・`recommendation` を持ち、本文が改変されていないか
   - 受け渡し本文の 2 ファイルが、記録の成功で削除されているか
4. 終端の前に、記録の失敗を注入する（受け渡し本文のファイルを欠いて、記録 script を呼ぶ）。終了コード、`errors`、既存の記録が変わらないことを確かめる
5. review の終端のあとで、記録の置き場（`.temp/forge/review/<review_id>/`）が無いことを確かめる
6. 確信度の記号が、調査の結論にだけ付いているか、機密値が無いかを点検する

対象は `docs/specs/consult/design/DES-078_consult_dialogue_flow_design.md`。consult topic は 1 件（ラウンド 1 で所見 1 件、ラウンド 2 は所見 0 件）。

### 観察

- **主張の訂正が 1 件あった。** consult brief は「置換は公式文書では未確認」と述べたが、skill-creator の参照を確かめずに書いたものだった。利用者の指摘で確かめ、公式の skills ページに記載があると訂正した。調査の漏れであり、consult の SKILL の記述の不備ではないと判断し、SKILL は直していない
- 訂正後の内容は、記録に反映されない。記録に残った consult brief には、訂正前の主張がある。議論の過程で consult brief を変更する機能は、要件の対象外（将来の候補）である
- 利用者の応答は、consult brief への反論と質問が中心で、consult は論点にとどまり、決着（採用）の表現で決着として扱った。次の項目へ進む場面は、項目が 1 件のため、確かめていない

## 限界

- **1 回・1 件だけの確認である。** 揺れを見るには、別の書類と別の session で繰り返す必要がある
- **この確認を行った session は、設計と実装の経緯を知っていた。** 「作り終えてから話しかける」が、SKILL の記述ではなく、経緯の知識と習慣で守られた可能性を排除できない。新しい session で、同じ手順を再実行することを勧める
- 記録の失敗の注入は、script の動作だけを確かめた。AI の振る舞いの確認が残っている
