# プラグイン実装ガイドライン

Claude Code プラグインのスクリプト（Python / Bash）と SKILL.md を実装するときの、プラグインに依らず使えるルール。

---

## スクリプト言語と依存 [IMPORTANT]

| 条件                                           | 言語   | 理由                                          |
| ---------------------------------------------- | ------ | --------------------------------------------- |
| データ変換・パース・YAML/JSON 操作             | Python | 構造化データ処理に強い                        |
| 外部コマンド呼び出し・ファイル操作・パイプ処理 | Bash   | シンプルで高速。Python 起動オーバーヘッドなし |
| 両方の特性が必要                               | Python | Bash の複雑化を避ける                         |

- Python スクリプトは標準ライブラリのみを基本とする。利用者の環境に依存の導入を求めないためである。別ライブラリの使用はユーザに許諾を取ること。標準ライブラリに YAML パーサーが無いので、スクリプトが読み書きする設定は JSON にするか、必要な範囲だけを自前で読む
- Bash スクリプトは外部コマンド（git, curl 等）の呼び出しに使ってよい

---

## テスト [CRITICAL]

プラグインとして配布する Python スクリプトにはテストを付ける。

| 対象                         | テスト             | 理由                                             |
| ---------------------------- | ------------------ | ------------------------------------------------ |
| 配布する `.py`               | 必須               | 利用者の環境で動くコードである                   |
| 配布する `.sh`               | 推奨（統合テスト） | 外部コマンド依存のため単体テストが難しい場合あり |
| SKILL.md                     | 例外               | AI の振る舞いの記述で、自動テストが難しい        |
| 利用者のローカルのスクリプト | 対象外             | 配布物ではない                                   |

- テストファイルは `test_{module}.py` と命名する
- テストを置くディレクトリの名前は、対象のスキル名と一致させる。スキルを改名したら、テストのディレクトリも同じ変更で改名する（片方だけ変えると、旧名のテストが新スキルを参照して静かに壊れる）
- AI の判断（Agent・SKILL の出力）を試すテストは、判定が揺れ、費用もかかる。CI のゲートに入れず、手動で実行するものとして分けて置く

---

## SKILL.md にインラインスクリプトを書かない [CRITICAL]

処理ロジックを SKILL.md の中にコードとして書いてはならない。AI がコードを解釈して実行するとき、勝手に改変・省略して失敗する危険がある。独立したスクリプトなら、AI は実行するだけで済む。

```markdown
# ❌ NG — SKILL.md 内にロジックを記述

以下の Python コードを実行してデータを集計する:

    import json
    data = json.load(open('plan.json'))
    # ... 50 行のロジック ...

# ✅ OK — 外部スクリプトを呼び出す

以下のスクリプトを実行して集計結果を得る:

    python3 "${CLAUDE_SKILL_DIR}/scripts/aggregate.py" {入力パス}
```

## スクリプトと文書の配置 [IMPORTANT]

| 配置先                      | 用途                                     |
| --------------------------- | ---------------------------------------- |
| `skills/{skill}/scripts/`   | スキル固有のスクリプト                   |
| `skills/{skill}/docs/`      | スキル固有の文書（そのスキルだけが使う） |
| プラグイン直下の `scripts/` | プラグイン共通のスクリプト               |
| プラグイン直下の `docs/`    | プラグイン共通の文書（複数スキルが使う） |

配置は「その資産を使うスキルが 1 つか、複数か」で決める。1 つなら `skills/{skill}/` 配下、2 つ以上ならプラグイン直下へ置く。

**他のスキルの `skills/{他スキル}/` 配下を直接参照してはならない**。参照元から見れば他人の持ち物への無断参照であり、参照先の内部構成が変わると静かに壊れる。複数のスキルから必要だと分かった時点で、その資産をプラグイン直下へ移す（コピーではなく移動）。

SKILL.md からの参照には `${CLAUDE_SKILL_DIR}` か `${CLAUDE_PLUGIN_ROOT}` を使う。

## 一時ファイルは `.temp/<plugin>/<skill>/` に `Write` ツールで書く [CRITICAL]

SKILL.md の手順でコマンドに渡す一時ファイル（Issue・PR の本文等）は、AI が `Write` ツールでプロジェクトルートの `.temp/<plugin>/<skill>/` に書く。ファイル名にはセッション ID を含める。

```text
${CLAUDE_PROJECT_DIR}/.temp/<plugin>/<skill>/<name>_${CLAUDE_SESSION_ID}.md
```

`<plugin>` にはプラグイン名を直に書く（プラグイン名を置換するプレースホルダは無い）。プラグインの階層を挟むのは、別のプラグインの同名 skill と置き場を分け、`.temp/` が ignore されていない環境でも `.temp/<plugin>/` だけを ignore すれば済むようにするためである。

1. 置き場を `mkdir -p` で作る
2. `Write` ツールで内容をそのまま書く
3. コマンドへファイルのパスを渡す（`--body-file` 等）
4. 成功したら削除する。失敗したら残し、再試行でそのまま使う

- **シェル（ヒアドキュメント・`echo` 等）で一時ファイルを書き出さない**。内容がコマンドに埋め込まれて毎回変わり、許可ルールで事前承認できない。内容中の区切り文字や引用符で書き出しが壊れる
- **`trap ... EXIT` に後始末を頼らない**。`trap` はそのシェルが終わると走るため、書く呼び出しと使う呼び出しが分かれると、使う前に消える
- **`mktemp -d` の既定（`$TMPDIR`）を置き場にしない**。プロジェクト外は sandbox の書き込み範囲に入らないことがある
- **ファイル名を固定しない**。セッション ID を含めないと、並行するセッションの内容と衝突する
- `.temp/` は、どのプロジェクトでも `.gitignore` する前提とする

スクリプトが読む受け渡しファイルも同じ置き場に置き、読み取り側のスクリプトが処理後に削除する。

## 配布物は開発用の文書を参照しない [MANDATORY]

利用者の環境で読まれるもの（SKILL.md / `agents/*.md` / `commands/*.md` / 配布した docs / templates）から、**開発リポジトリにだけ実在する文書**（仕様書・設計書・開発ルール）を参照しない。パスの直書きも、仕様 ID による出典表記も禁止する。利用者の環境に実体が無く、参照が解決できず、規範の根拠も検証できないからである。

```text
❌ 複数文書間の優先順位は DES-028 §3.4.1 に従う
❌ 詳細は docs/specs/foo/design/DES-029... を参照
```

- script（`.py` / `.sh`）のコメントと docstring、`scripts/` 配下の開発者向け README は対象外とする。基準は拡張子ではなく、誰が読むかである。SKILL.md は文脈へ注入され、配布した docs は SKILL から名指しで読まれるが、script のソースを開くのは実装を追う開発者だけである。実装の意図がどの決定に由来するかを実装のすぐ隣に残せる価値のほうが大きいので、script のコメントには実在する仕様 ID を書いてよい。template は利用者の環境へ入って読まれるため、対象に含める
- ID の体系や書式を示す抽象例は許容する。プレースホルダ番号（`DES-001`）や、対象プロジェクトの構造を示すプレースホルダのパス（`docs/specs/<feature>/design/*.md`）は、実在の文書を指さないため対象外である
- 規範の根拠を示すには、規範の本文を参照元にそのまま書くか、配布物の中に別の文書を作って参照する。分量が小さく 1 箇所でしか使わないなら前者、分量が大きいか複数から使うなら後者が向く
- 逆の向き（開発用の文書が、配布物の実装を参照する）は許容する

## 他のコンポーネントへの窓口は SKILL だけ [MANDATORY]

他のコンポーネントに依存するとき、インターフェースは SKILL に限る。依拠してよいのは、SKILL.md が公開する引数と出力の契約だけである。

- 他のコンポーネントのスクリプトを直接呼ばない
- 内部の設計 ID や内部文書の記述をインターフェースにしない
- 設計書を読んで同じ動作を自分で実装しない

内部は予告なく変わる。スクリプトの引数・出力・配置も内部実装であり、公開された契約ではない。

---

## 使わないコードは削除する [IMPORTANT]

非推奨マーカーやコメントアウトで残さない。残ったコードは勘違いの原因になる。

- 削除の経緯はコミットメッセージに書く
- 「将来使うかもしれない」は削除しない理由にならない。git の履歴から復元できる
- テストファイルも本体と同時に削除する

---

## AI が解釈する入力にスクリプトのパーサーを使わない [CRITICAL]

ユーザーの入力（コマンドの引数など）には自然言語が混ざる。厳密なトークンのパーサーではなく、AI が直接解釈する。

- スクリプトは構造化データ（YAML / JSON）の処理に限る
- 引数が不足・曖昧なら、ユーザーに確認して補う
- コマンドの構文は SKILL.md に書き、AI がそれを参照して意図を読み取る

---

## フォールバックを反射的に書かない [MANDATORY]

フォールバックそのものを禁じるのではない。**その異常系に対する正しいリカバリーとして、具体的に説明できるフォールバックは問題ない。** 禁じるのは、説明できないまま「一応の保険」として反射的に書く癖である。

### 禁止するパターン

- 失敗したときに「別のモードに切り替えて続行する」「非同期に委ねて次へ進む」などと書くが、それが呼び出し元にとって何を意味するか（確定した結果を得られるのか、処理が実際に進むのか）を詰めていない
- 例外を握りつぶして、既定値やダミーの結果で代替する
- 何が起きるかを自分で説明できないまま、設計書・要件定義書にフォールバックの文言を書く

### 判断の手順

1. フォールバックを書こうとしたら、まず「これはこの異常系に対する正しいリカバリーか」を自問する。説明できないなら書かない
2. リカバリーとして採用するときも、呼び出し元が受け取る結果（確定した成功か失敗か、何が保留されるか）を明記する
3. 適切でない、または説明できないなら、フォールバックで隠さず**エラーとして明確に報告**する。呼び出し元が次の判断（再試行・手動対応・中断）をできるだけの確定した情報を返す。そのうえで原因（リトライできない処理順序、タイムアウト値の欠如、境界条件の見落とし等）を特定し、エラーが構造的に起きないよう設計・実装を見直す

### 理由

反射的なフォールバックは一見ロバストに見える。しかし実態を詰めずに書かれることが多く、失敗を隠して、呼び出し元と利用者が異常に気づく機会を奪う。フォールバック先の経路が呼び出し元の前提（同じターンの中で結果を受け取る等）と矛盾すると、処理が何も進んでいないのに「続行できた」ように見える。問題は、フォールバックを選ぶことではなく、**吟味せずに反射的に選ぶこと**である。

## バージョン関連ファイルは通常の作業で編集しない [CRITICAL]

機能追加・修正・リファクタリングなどの通常の作業で、バージョン関連のファイルを編集してはならない。バージョン更新は、リリースの手順に責任を一本化する。個別の作業の中で先回りして上げない。

### 編集しない対象

| 対象                                          | 内容                                   |
| --------------------------------------------- | -------------------------------------- |
| `plugin.json` の `version`                    | 各プラグインのバージョン               |
| `marketplace.json` の各プラグインの `version` | カタログに載せるバージョン             |
| README のバージョン表                         | 数値が変わる差分                       |
| `CHANGELOG.md` などの変更履歴                 | 全エントリ（追加・修正・削除のすべて） |
| git タグ                                      | 作成・移動・削除のすべて               |

### 例外

- 新規プラグインの追加時に、初期値（`0.0.1` など）を新しく書くこと。既存の値の変更ではない
- リリースの手順を明示して実行するとき
- 本ルール文書自体の改訂

### 理由

| 理由                       | 説明                                                             |
| -------------------------- | ---------------------------------------------------------------- |
| リリース単位の一意性       | 誰がいつ何をまとめてリリースするかを、リリースの手順に集約する   |
| 変更履歴の自動生成との衝突 | 手動の編集と自動生成が二重になると、整合性が崩れる               |
| 並行する変更の衝突の回避   | 複数の変更が同じバージョン行を編集すると、マージで衝突が頻発する |

バージョン更新が必要だと判断したら、自分で上げず、ユーザーにリリースの手順の実行を提案する。
