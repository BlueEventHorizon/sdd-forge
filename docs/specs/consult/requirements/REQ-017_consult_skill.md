# REQ-017 consult 対話進行スキル要件定義書

## 1. 概要

consult の主たる責務は、利用者との対話である。**利用者に内容を分かりやすく伝え、正しい結果（判断）を得ること**を主眼とする。表示は、そのための手段の 1 つである。

対話の情報は次々に流れ、利用者は、流れた情報を探し出すことが難しい。
そこで consult は、利用者が全体の状況と個々の consult topic の判断を把握できるように、次を担う。

| 責務             | 内容                                                                                                                         | 要件                        |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------- | --------------------------- |
| 全体の提示       | すべての consult topic・現在位置・前回から変わったことを、一覧（進捗表）として、定めた表示形式で、進むたびに更新して再掲する | FNC-002                     |
| 個別の提示       | consult topic ごとに、調査を終えてから、consult brief（要旨と推奨案の 2 欄、10 行程度）を述べる                              | FNC-001、003〜006、012、013 |
| 進行             | 用途ごとに定めた順に自ら進め、質疑に応じ、利用者が扱いを決めるまで待つ                                                       | FNC-002、007、010           |
| 判断の取得と返却 | 利用者の判断を一覧に反映し、委譲されたときは上流へ返す。中断・保留・対象外を扱う                                             | FNC-008、009                |
| 記録             | consult brief の要旨と推奨案を、script で JSON に記録する                                                                    | FNC-014                     |

利用者が決めていないことは実行しない（BL-001）。

対象は、利用者と対話するすべての場面である。報告・質問・相談・完了報告を含み、設計方針の相談、調査結果の報告と合意形成、たたき台のレビュー、口頭のディスカッションもここに入る。媒体を問わない。

本スキルの用途は 3 つある。何をするか（修正か作成か）と、入力の出どころ（reviewer か対話か）で分かれる。対話による修正と新規作成をまとめて、対話の用途と呼ぶ。

| 用途           | 何をするか | 入力                                            | 決まったことの扱い                                               | 表示の手段                                                                       |
| -------------- | ---------- | ----------------------------------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| review         | 修正       | review が渡す評価の JSON（reviewer の所見）     | review 本体へ返す。修正は review 本体が行う                      | review の手順が定める                                                            |
| 対話による修正 | 修正       | 会話の文脈。consult が consult topic を取り出す | その都度その場で反映する                                         | コンソールに概観を毎回再掲し、詳細（リンクを含む）は script が作る HTML に載せる |
| 新規作成       | 作成       | 会話の文脈。consult が consult topic を取り出す | consult topic ごとには反映しない。決着を求めず、最後に文書を書く | 対話による修正と同じ                                                             |

報告・質問への回答のように、決めることも反映することも無い対話は、対話による修正に含める。要件定義書をゼロから作る対話（`/forge:start-requirements` の対話形式）は、新規作成の典型である。

レビュー所見の評価・修正・完了判定は本スキルの対象ではなく、`/forge:review` が自ら行う（REQ-013）。
ただし、所見を 1 件ずつ提示して採否を得る**対話進行**は、`/forge:review` から本スキルへ**委譲**する。
review と consult は対等なサブシステムだが、実行時には review が consult を呼び出す
一方向の依存を持つ。両者は提示の規範（本スキルの SKILL が持つ）を共有し、
対話進行の実装も本スキルへ一本化する（同じロジックを review 側に複製しない）。

### 1.1 対象システムの性質

本スキルは開発者が自分の端末で使う対話ツールであり、外部公開・本番運用・個人情報の保持を伴わない
（[spec_priorities_spec.md](../../../../plugins/forge/docs/spec_priorities_spec.md) §10.1 の
「上記いずれにも該当しない」に該当する）。性能・可用性・運用性の定量目標は持たない。ただし提示対象に機密情報が含まれうるため、その扱いは
NFR-004 で定める。

## 2. 用語

| 用語          | 定義                                                                                                                                                                                                                                    | 出どころ         |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| evaluation    | review の evaluator が書く判定 1 件。1 個以上の所見（finding）を引く                                                                                                                                                                    | REQ-029 DM-201   |
| consult topic | 利用者の理解・判断を要する、consult の対話の 1 単位。review では、利用者に採否を聞く evaluation 1 件が 1 つの consult topic になる（確認なしに直した評価・位置未確定・ドロップした評価は、一覧に載せるだけで consult topic にならない） | FNC-001          |
| consult brief | consult topic 1 件について、consult が利用者に述べる、要旨と推奨案の組                                                                                                                                                                  | FNC-003          |
| 提示状態      | consult topic の一覧と、各 consult topic の状態・結果。置き場は用途ごとに 1 つ                                                                                                                                                          | FNC-002、NFR-001 |
| 対話の用途    | review から委譲される場合を除く、利用者とのすべての対話。対話による修正と新規作成の 2 つからなる                                                                                                                                        | §1               |

consult brief の要旨と推奨案は、evaluator が書く判定の根拠（`reason`）や、reviewer が書く所見の本文とは別のもので、consult が作る。

## 3. スコープ

### 3.1 対象

- consult topic の受領と把握
- consult brief（要旨・推奨案・確信度）の作成と提示
- 複数 consult topic の進行管理と、進捗・結果の把握
- 理解のための質疑応答
- 判断の取得
- 中断・保留・対象外の扱い
- consult brief の記録
- 対話の用途での、文脈からの consult topic の取り出しと、HTML による詳細の表示

### 3.2 対象外

| 対象外の事項                                             | 補足                                                                                                    |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 議論対象そのものの生成                                   | レビューの実行、設計案の立案。ただし consult topic の確信度を上げるための検証は行う                     |
| 利用者が決めていないことの実行                           | ファイル修正、Issue 起票、commit、外部送信（BL-001）                                                    |
| レビュー所見の仕分け                                     | `/forge:review` の責務                                                                                  |
| 提示対象の正しさの保証                                   | 誤りの指摘は利用者の応答として扱い、本スキルは判定しない                                                |
| consult brief の要旨と推奨案を、議論の過程で変更する機能 | 議論の結果、変わることがある。将来の要件の候補                                                          |
| 前提である JSON の内容を、議論で変更する機能             | 議論で前提が覆ることがある。将来の要件の候補                                                            |
| review での進捗の状態の永続化                            | review では提示状態を会話にだけ持つ（NFR-001）。consult brief の記録（FNC-014）は、提示状態とは別である |

## 4. 前提条件

- review は、依頼・所見・評価を JSON で受け渡す（REQ-029）。所見は `finding_id`・`location`・`body` を持つ（DM-302）。evaluation は `finding_ids`・`disposition`・`severity`・`reason` を持ち、`valid` のときは `confidence` と `fix_confident` を持つ（DM-201）。
- review から委譲されたとき、consult は、review 本体が段階的提示へ回す evaluation を、consult topic として受け取る。
- 対話の用途では、入力は会話の文脈にある。review の評価のような入力のファイルは無い。
- consult は、どちらの用途でも、その会話がそのまま振る舞いを切り替える形で動く。

## 5. 機能要件

### FNC-001: consult topic の受領と検証 [MANDATORY]

consult topic を把握し、**提示する前に確信度を上げること**。

- 委譲されたときは、上流（委譲元）が吟味して渡した consult topic を使う。位置・根拠・確信度・修正の可否は、上流が持っている内容をそのまま使うこと
- 対話の用途では、本スキルが文脈（会話の流れ、渡された文書・コード）から consult topic を取り出す
- 各 consult topic は、一覧の中で一意に指せる識別子を持つこと。**識別子は議論の途中で変えないこと**。利用者が consult topic を指し示す手段になるため、番号の振り直しをしない
- 確信度が低く検証が可能な consult topic は、提示する前に検証すること（実物を読む・実行する・調べる）。
  検証せずに推測のまま提示し、利用者に検証を促されることがないようにする
- **調べれば分かることを、調べずに「未確認」「未調査」として述べないこと**。調べる手段（実物・使える skill や script・会話の記録）を探してから述べる。手段が無いときだけ、何を探して無かったかを添えて、確認できないと述べる
- consult topic が 0 件の場合、提示を行わずその旨を述べて終えること（空の対話を開始しない）

### FNC-002: 複数 consult topic の進行管理 [MANDATORY]

consult topic が複数ある場合、一覧で、**すべての consult topic が何で、現在位置はどこで、何が変わってきたか**を把握できること。

- 重要度は、review から委譲されたときだけ示し、**レビュー所見と同じ語彙**を用いること。対話の用途では重要度を示さない（根拠を持って重要度を付ける上流が無いため）
- 状態は少なくとも「未着手」「進行中」「決着」「保留」「対象外」「取り下げ」を区別できること。「保留」は今回は扱わないが扱う可能性がある consult topic、「対象外」は最初から今回の範囲外と決めた consult topic、「取り下げ」は consult topic として誤りだったため取り消した consult topic を指す。review から委譲されたとき、採否を聞かない評価は、一覧に載せたうえで「報告のみ」の状態で示す。新規作成では、決着の代わりに「議論済み」の状態を使う（FNC-010）
- 一覧は、進捗表として、進むたびに更新して再掲すること。決着した consult topic には決まったことを結果として、決着していない consult topic には何が解決していないかを課題として示す。**結果と課題は分けて示し、1 つの欄にまとめない**（1 つの欄が状態によって違う意味を持つと、読み手が行ごとに意味を読み分けることになる）
- **やっていないこと・解決していないことを、分類せずに並べないこと**。分類の無い「していないこと」は、漏れか範囲外かが読み手に分からず、読み手が調べに行くことになる。各項目を次のどれかにして示す。分けられないなら、示す前に調べて分ける
  - やるべき: 推奨として示し、次の行動に入れる
  - 判断が要る: 推奨と理由を添えて、判断を求める
  - やらない（範囲外・不要）: 理由を 1 句添えるか、示さない
- 一覧は、現在位置（いま扱っている consult topic と、残りの件数）と、前回の一覧から変わったことを示すこと
- 一覧は、すべての項目を 1 行ずつ簡略に示し、いま扱っている consult topic だけを詳しく示すこと。全体を一目で見ることと、いまの論点を詳しく読むことを両立させる。consult brief は、その詳しい表示の中で示す
- 各行は、何の論点かをその行だけで分かるように示すこと。位置だけで項目を表さない（読み手が位置から内容を思い出さなければならなくなる）
- 議論の中で新しく生まれた consult topic は、一覧に新しい行として加えること。既存の行の識別子は変えない（FNC-001）
- 一覧は、定めた表示形式に従って示すこと。表示形式は用途ごとに定め、その用途の手順が持つ（NFR-002）。提示のたびに AI が形式を作らない
- **進行の主導権を本スキルが持つこと [MANDATORY]**。「次はどれを見ますか」と利用者に選ばせない。
  用途ごとに定めた順に自ら進め、利用者がすることは止める・飛ばす・順序を変えることだけでよい状態を保つ。
  review では重要度の高い順とする。対話の用途では、他の consult topic の前提になるものを先にし、一覧に各 consult topic が何を待っているかを示す
- 同種の判断が繰り返される consult topic は、一括の判定表で提示してよいこと。往復が判断の質を上げない場面では
  往復を増やすことのほうが害になる。ただし一括へ切り替える件数の閾値を AI が独自に定めないこと
  （TBD-003）

### FNC-003: consult brief は、要旨と推奨案の 2 欄とする [MANDATORY]

各 consult topic は、**利用者が原文に戻らずに判断できる**形で提示すること。consult brief として、次の 2 欄を述べる。

1. **要旨** — 本質を踏まえ、**わかりやすく簡潔に**書いた説明。背景（何が問題で、なぜ今それが論点になったのか）を含め、判断を左右しているのはどこかを示す
2. **推奨案** — 要旨を踏まえた、簡潔な推奨。AI が正しいと判断した案を 1 つだけ、理由（根拠と代償）を添えて述べる。すでに判断がついているなら伏せない

- 要旨を述べずに選択肢から始めないこと
- 2 欄の前に、その consult topic で利用者が何を決めるのかを 1 行で示すこと。判断の対象を最初に示し、読み手が要旨を読みながら問いを再構成しなくて済むようにする。この 1 行は要旨の代わりにしない。10 行程度の行数に含めない（FNC-006）
- 提示は要約であってよいが、**原文への到達手段（位置・出典）を必ず併記すること**
- consult brief は、定めた表示形式に従って示すこと。表示形式は用途ごとに定め、その用途の手順が持つ（NFR-002）
- 選択肢を示すのは、決定が利用者の価値判断に属し、AI が 1 つに絞れないときだけとする。このとき示す選択肢は、AI が正しいと判断した案だけである。AI が正しくないと判断した案は示さない。各選択肢が何であるかと、選ぶと何が変わるかを示し、数を絞ること
- **正しくない候補を示すことを厳禁とする**。正しくない案を並べると、利用者が誤ってそれを選ぶ余地をあえて作り、判断の時間も無駄にする。劣る案を加えると、それを上回る案へ判断が誘導されることも知られている（おとり効果。Huber, Payne & Puto, 1982, Journal of Consumer Research）。正しい案が 1 つなら、選択を求めず、その 1 つを丁寧に説明する
- 選択肢を示すときは、どれを選ぶかを左右する利用者の価値・優先順位が何かを示すこと。選択を求めてよいのは、妥当な案が複数あり、その選び分けが利用者の価値・優先順位に依存するときだけである（共有意思決定の [three-talk model][three-talk]）

提示の具体的な作法は、本スキルの SKILL が持つ。

### FNC-004: 確信度の明示 [MANDATORY]

判断を左右する主張には、調査の結論としての確信度を示すこと。

- 次の 3 段階を区別できること。`/forge:review` が評価に付けて渡す記号と同じ体系とする
  - ✅: 調査した上で、主張は正しく、その対処まで責任を持って実行できる
  - ☑️: 調査した上で、主張は正しいと結論した。ただし対処の仕方に確信が無い
  - 無印: 調査しても主張の妥当性に確信が持てない、または調べる手段が無い（どちらであるかを示す）。調べる手段があるのに調べないことを、無印の理由にしない（FNC-001）
- **無印を既定とすること**。表示を欠いたときに確信度が高く見えない向きにすること
- ✅ と ☑️ は、調査の結論にだけ付けること。調べずに「正しいはず」と感じただけのものには付けないこと（FNC-001）
- 確信度の表示を全ての記述に付けないこと（分量を損なうため。FNC-006）
- **説明の長さと断定の強さを、確信度に合わせること**。確信の無い主張を、長い説明や言い切りで補わないこと。説明が長いほど、正しさと関係なく読み手の確信が上がり（[Steyvers ら][steyvers]）、説明があると推奨が誤っていても受け入れられやすくなる（[Bansal ら][bansal]）。推奨を 1 つ言い切る consult brief は、この危険を直接受ける

### FNC-005: 文脈の再掲 [MANDATORY]

過去のやり取りを参照するとき、参照で済ませず要点を再掲すること。

- 「前述の通り」「先ほどの案」といった参照だけで済ませないこと
- consult topic の識別子や、案に付けた名前を再び用いるとき、それが何を指すかを併記すること
- 参照リンクや位置の明示を、再掲の代替としないこと

理由: 流れたやり取りから該当箇所を探し出すには労力がかかりすぎる。探して読み直せることを前提にした
提示は、その場で完結しない。

### FNC-006: consult brief は簡潔にする [MANDATORY]

consult brief は、**わかりやすく簡潔に**書くこと。簡潔さは内容で決まる。要点に絞り、同じことを重ねず、判断に要らないことを書かない。行数を守るために、判断に必要な要点を削らない。

分量の目安として、consult brief の要旨と推奨案を合わせて、10 行程度に収める。この値は暫定である（TBD-006）。

- consult topic の一覧（進捗表）の再掲と、原文への到達手段（位置・出典）の併記は、この行数に含めない
- **同じ内容を重ねて書かないこと**
- 提示には、**その consult topic 単体で判断できるだけの要点を必ず書くこと**
- 並列する項目は表にまとめ、散文で列挙しないこと
- 詳細は求められてから提示すること。先回りして網羅しないこと

### FNC-007: 質疑応答 [MANDATORY]

利用者が判断ではなく**理解**を求めた場合、判断を促さずに応答すること。

- 掘り下げの要求（「詳しく」「なぜそうなるのか」「他の選択肢は」）に対し、判断を求める問いを
  返さないこと
- 質疑の往復回数に上限を設けないこと
- 質疑の結果として提示内容の誤りが判明した場合、当該 consult topic を一覧に残したまま「取り下げ」の状態にできること。
  ただし**取り下げた事実・理由・誰の指摘によるもの（利用者の指摘か AI の自己訂正か）を一覧に示すこと**。示さずに consult topic を消すことを禁じる
- 取り下げの判断が分かれる場合（誤りとまでは言えない場合）は取り下げず「進行中」のまま残し、利用者の指示を待つこと。**判断が付かないことを取り下げの理由にしないこと**

### FNC-008: 判断の取得 [MANDATORY]

各 consult topic について利用者が下した判断を、一覧に反映し、委譲されたときは上流へ返すこと。対話による修正では、終了時の一覧が利用者への結果である。新規作成では、一覧の内容から書いた文書が結果である。

- 判断は少なくとも「採用する」「採用しない」「保留する」を区別できること
- 「採用しない」「保留する」には理由を伴わせること。理由を省略しないこと
- 利用者が明示的に判断を下していない consult topic を、既定値で埋めないこと（未判断は未判断として残すこと）
- **AI が判断した consult topic は、その旨を判別できる形で示すこと**。人間の判断と混在させないこと

### FNC-009: 中断・保留・対象外 [MANDATORY]

対話は利用者の都合で任意の時点で終えられること。扱わないと決めた consult topic も見える形で残すこと。

- 「残りは全部あとで」「ここで終える」に対応し、その時点までの判断を確定すること
- 中断した場合、**何件が未判断のまま残ったか**を明示すること。未判断を「対応不要」へ畳み込まないこと
- **今回扱わないと決めた consult topic を、一覧から削除しないこと**。「対象外」の状態で残し（結果に、なぜ扱わないかを示す）、利用者が確認できる状態にすること
- review から委譲されたとき、中断は 1 回の対話の中で完結すること。**次の起動で続きから再開する経路は持たない**——提示状態は会話にだけあり、永続化されないため。対話の用途での再開は未確定である（TBD-009）

### FNC-010: 決着の主体は利用者 [MANDATORY]

consult topic の扱い（採否・保留・対象外など）を決めるのは、利用者であること。決着は、利用者が決めたときに成立する。

- 利用者が考えている間は、その思考に付き合い、決着を急がせないこと。判断を求める問い（「これで進めてよいですか」を含む）を発しないこと
- 利用者が consult topic の扱いを決めるまで、次の consult topic へ移らないこと
- 決着した後は、本スキルが自分で次の consult topic へ進むこと。次をどうするかを利用者に選ばせないこと（FNC-002）
- 利用者は、順序を変える・飛ばす・終えることができること
- 新規作成では、決着を求めない。要旨と AI の見解を述べたら、その consult topic を「議論済み」とし、次へは利用者の指示で進む。決定を求めるのは、利用者が決めると明示したときだけとする（壁打ち・たたき台は、決める流れの依頼ではないため）

### FNC-012: consult brief はメインの claude が作る [MANDATORY]

consult brief の要旨と推奨案を作るのは、メインの claude である。利用者と対話しているその会話（委譲されたときは review 本体と同じ会話）の中で作る。

理由は、メインの claude が、内容をよりよく理解でき、さらに利用者へ説明できるためである（作成と説明を同じ主体が担う）。

### FNC-013: 各 consult topic の直前に consult brief を作り終えてから話しかける [MANDATORY]

consult は、各 consult topic に入る直前に、その consult topic の consult brief を作り終える。consult brief に付ける確信度（✅ / ☑️）は調査の結論であるため、作成には調査の時間を含む。**作り終えるまで、利用者に話しかけない。** 作った consult brief を表示してから、利用者の応答を待つ。

### FNC-014: consult brief の要旨と推奨案を、consult topic ごとの独立した値として記録する

consult は、consult brief の要旨と推奨案を、consult topic ごとの独立した値として、script で JSON に記録する。AI は、JSON を組み立てない。

記録する値は、consult topic を一意に指せる識別子と対にする。対話の用途での識別子と置き場は未確定である（TBD-008）。review では、識別子は `review_id`・`round_number`・consult が採る通し番号の組とする。通し番号は、その round で記録した順に、script が採る（AI は数えない）。評価の ID は用いない（evaluation は 1 対 1 に所見と対応せず、同じ `finding_ids` を持つ evaluation が複数ありうる）。

記録した JSON を、誰が読むか、どう表示されるかは、consult の関知するところではない。読み手が無くても、consult は動作する。

### BL-001: 利用者が決めていないことを実行しない [MANDATORY]

本スキルは、利用者が決めていないことを実行しないこと。

- 決着していない consult topic について、ファイルの修正、Issue の起票、commit、外部への送信を行わないこと。それらを担う別スキル・別 Agent も起動しないこと
- 対話による修正では、利用者が決めた consult topic を、その場で反映してよい
- 新規作成では、consult topic ごとには反映しない。利用者の指示を受けて、対話の内容から文書を書く
- review から委譲されたときは、実行を review 本体に任せ、判断を review 本体へ返すところまでを終端とすること

理由: 提示と実行が混ざると、対話の途中で実行が始まり、利用者が決めていない変更が成果物へ入る。防ぐのは決めていないことの実行であり、決めたことの実行ではない。対話の用途には判断を返す上流が無く、決めたことを実行するのは同じ会話である。consult brief の記録（FNC-014）は本スキルの成果物であり、この禁止の対象外である。

### BL-002: 提示の忠実性 [MANDATORY]

提示にあたり、対象の意味を変えないこと。

- 要約によって判断の分岐点を落とさないこと
- 複数の項目を統合して提示する場合、統合したことと統合の理由を示すこと。統合によって個別項目が
  利用者から見えなくなる状態にしないこと
- 提示対象に含まれていない評価・推測を、対象の記述であるかのように混ぜないこと

## 6. 非機能要件

### NFR-001: 提示状態の置き場は用途ごとに 1 つとする [MANDATORY]

提示状態の置き場は、用途ごとに 1 つとすること。

- review から委譲されたとき: 提示状態を会話コンテキストにだけ持つ。状態ファイル・作業ディレクトリ・DB を持たない。一覧は再掲するたびに更新して会話に残し、再掲した最新の一覧が現在の提示状態である。提示状態は永続化されず、会話が終われば失われる
- 対話の用途: consult が文脈から取り出した表示の材料（consult topic・要旨・推奨案・状態・結果・課題・位置）を script に渡し、script が検査して HTML を作る。この材料が提示状態の置き場である。コンソールには、材料に基づく概観を毎回再掲する。AI は HTML を直接書かない
- consult brief の記録（FNC-014）は提示状態ではなく、本項の対象外である

理由: 状態の置き場が複数あると、どれが正かが失われる。置き場を 1 つに集約することで、表示と実際の進行の食い違いを構造的に防ぐ。対話の用途でファイルを置き場にするのは、詳しい情報（リンクを含む）を整然と示す HTML の材料が要り、流れて消えるコンソールだけでは全体を追えないためである。

### NFR-002: 用途非依存、および review に固有の処理の分離 [MANDATORY]

本スキルは特定の用途に固有の語彙・体系を、提示構造に持ち込まないこと。

- レビュー固有の概念（往復ラウンド・承認判定）を必須要素にしないこと
- 用途ごとの差異（入力・表示の手段・進める順・記録）は、用途ごとの手順文書と script で吸収すること
- 用途が増えるたびに本スキルの構造を拡張しないこと。SKILL は、用途を見分けて、その用途の手順文書を読ませることだけを持つ
- consult は SKILL と script で実装する。consult の中枢機能（利用者との対話の方法）は、consult の SKILL に記述し、外部のファイルへ分けない
- 用途に固有の処理は、consult の SKILL とは別のファイル（用途ごとの手順文書と script）に置く。review では、受け取る評価の扱い、重要度、一覧と consult brief の表示形式、まとめて直す申し出、結果の返し方、記録の呼び方がこれにあたる。対話の用途では、文脈からの consult topic の取り出し、コンソールの概観と HTML の表示形式、HTML を作る script の呼び方がこれにあたる。SKILL は、用途に依らない対話の方法だけを持つ。これにより、他の用途の処理を、consult の対話の方法を作り直さずに追加できる

### NFR-004: 機密情報の非提示 [MANDATORY]

提示対象に機密情報が含まれる場合、その値そのものを提示にも記録にも含めないこと。

- 提示するのは「どこに」「どの種類の」機密が含まれるかまでとすること
- 利用者が値の表示を求めた場合も、本スキルは表示せず、利用者自身が原本を確認する経路を示すこと

### NFR-005: 失敗の可視性

consult topic の把握に失敗した場合（対象が不明・対話の目的が不明）、既定値で補って対話を開始しないこと。
何が不足しているかを利用者へ述べて終えること。

consult brief を作れないとき（原文へ到達できない）、および consult brief の記録に失敗したときも、既定値で補わず、理由・失敗を利用者に伝えること。
