# REQ-034 start-implement 要件定義書

## 1. 概要

`/forge:start-implement` は、実装計画書のタスクを選び、実装・レビュー・計画書の更新までを実行する。利用者は、計画書が示す作業を、中断やエラーがあっても状態を失わず、完了の確認を伴って、順に終わらせられる。

この機能が解決する課題は次のとおりである。

- 作業の途中で止まったとき、どこまで終わったかが分からず、続きから再開できない
- 実装を任せる側が内容を把握していないと、返ってきた成果が正しいかを判断できない
- 実装とレビューの往復が多いと、作業が遅くなる

対象は、計画書のタスクを実装する開発者（人・AI）である。

本要件は、タスクを選んでから完了とするまでの振る舞いを定める。計画書が持つ情報の基本は [REQ-024 実装計画書 要件定義書](../../forge/requirements/REQ-024_implementation_plan_spec.md)、executor agent からの結果の受け渡しは [REQ-001 オーケストレータパターン要件](../../forge/requirements/REQ-001_orchestrator_pattern.md)（FNC-004）が定める。計画書へのタスクの追加は `/forge:start-plan` の責務であり、本要件の対象外である。

### 1.1 対象システムの性質

forge プラグイン内部の文書運用であり、外部公開・本番運用・個人情報の保持を伴わない開発支援ツール相当のスコープである（[spec_priorities_spec.md](../../../../plugins/forge/docs/spec_priorities_spec.md) §10.1 の「上記いずれにも該当しない」に該当する）。

## 2. 前提条件

- 実装計画書が存在すること（存在しないときの扱いは FNC-001）
- 実装は 1 つのタスクを単位に executor agent が行い、結果を return value で返すこと（REQ-001 FNC-004）

## 3. 用語

| 用語             | 定義                                                                                                                                   |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| オーケストレータ | `/forge:start-implement` を実行し、全体の進行を担う主体。タスクの進行状態を書く唯一の主体                                              |
| executor agent   | オーケストレータから 1 つのタスクを任され、実装して結果を返す Agent。利用者ではない。本文では、同じ文の 2 回目以降を「executor」と略す |
| タスクグループ   | 完了時点でビルドが通る、複数のタスクのまとまり。構成の基準は FNC-006 が定める                                                          |

## 4. 機能要件

### FNC-001: タスクの選択と提示

利用者が feature と、任意でタスク数を指定して起動したとき、実行可能なタスクを優先度順に選び、実行の前に利用者へ提示すること。実行可能なタスクの定義は、[REQ-024 実装計画書 要件定義書](../../forge/requirements/REQ-024_implementation_plan_spec.md) FNC-002 に従う。

- 計画書が存在しないときは、作成を案内して終了すること
- 実行可能なタスクが無いときは、その事実を知らせて終了すること
- 実行可能になるのを待つタスクが、選択の枠を占めないこと
- タスク数を指定しないときは、優先度が最も高いタスク 1 件を選ぶこと
- 同じタスクグループの未着手のメンバーは、一緒に選ぶこと。ただし、先行タスクが完了・実装済みでも、同じ選択の先行メンバーでもないメンバーは、選ばず、未着手のまま残すこと
- 実行中・実装済み・失敗・完了のタスクは、選ばないこと

理由: 選択が解釈に依存すると、同じ計画書から異なる実行順序が生まれる。待つタスクが枠を占めると、実行できるタスクがあるのに実行されない。

### FNC-002: 進行状態の保持と再開

各タスクの進行状態（値と意味は REQ-024 FNC-002 が定める）を、計画書に持つこと。進行状態を書くのは、オーケストレータだけとすること。

- 実装を始める前に、そのタスクを実行中にすること
- 起動したとき、実行中のタスクが残っている場合は、前回の残りか、別の実行が進行中かを利用者に確認すること。前回の残りであれば、FNC-003 に従い、実行中のまま残ったタスクだけを失敗にすること。別の実行が進行中であれば、起動を中止して終了すること
- 開始前に見送ったタスクは、未着手のままとすること

理由: 実行中の印が無いと、中断のあとにタスクが途中かどうかが分からない。前回の残りと進行中の実行は、機械的に区別できないため、利用者の確認が要る。別の実行が進行中のまま起動すると、同じ計画書への状態の書き込みが競合する。executor agent が計画書へ書くと、並行して動く executor の書き込みが競合する。

### FNC-003: エラーの扱いと再実行

回復できないエラーで停止したタスクは、失敗の状態にし、実行中のまま残さないこと。停止したことは、利用者に報告すること。エラーの定義と分類（回復可能・回復不能）は、[error_classification_spec.md](../../../../plugins/forge/docs/error_classification_spec.md) に従う。

- 失敗のタスクは、自動では選ばれないこと。利用者が再実行を選んだときだけ実行すること
- 失敗のタスクに依存するタスクは、実行可能にならないこと
- 中断では、実行中のタスクだけを失敗にすること。実装済みのタスクは残すこと
- タスクが失敗の状態になったとき、または最終確認（FNC-005）に通らなかったとき、そのタスクに（推移的に）依存する実装済みのタスクは、未着手に戻すこと。依存しない実装済みのタスクは残すこと
- タスクグループの中でタスクが失敗の状態になったときは、そのタスクと、未着手に戻したタスクだけを再実行すること
- その場で続けて再実行できるのは 1 回までとすること。失敗にしたタスクは、別の起動で再実行できること

理由: 失敗のタスクを未着手に戻すと、次回の起動で同じタスクが最優先で選ばれる。実行中のまま残すと、中断の残りと区別できない。実装済みのタスクの成果を捨てると、意味や目的が共通する範囲でまとめたタスクグループでは、やり直しの無駄が大きい。依存するタスクが先行する実装済みのタスクの成果の上に作られている場合、先行が失敗の状態になると、その成果は前提を失う。

### FNC-004: 任せる前の把握と準備

オーケストレータは、executor agent にタスクを任せる前に、そのタスクの内容と、何を作らせるかを把握していること。把握しないまま任せてはならない。

- 把握するのは、タスクの説明、受け入れ基準、今回の範囲と範囲外、根拠の設計書と要件定義書である
- 必読文書は、計画書のタスクの必読文書と、設計の識別子の設計書と、その設計に対応する要件定義書を土台にすること。要件定義書は、計画書のタスクの必読文書に書かれていなくても、土台に入ること。実行時に、既存コードと、タスクに応じた実装ルールを補うこと。オーケストレータは、集めた文書を読むこと
- 今回の到達点と範囲外を導出し、executor agent とレビューに同じ内容を渡すこと（[REQ-013 レビューポリシー要件](../../forge/requirements/REQ-013_review_policy.md) FNC-1319）
- 実装の指示は、オーケストレータが把握した内容から作ること
- 検証（ビルド・テスト）の要否は、ビルドは計画書の `build_check` から、テストはタスクの内容から決めること（5.2）

理由: 内容を知らないまま任せると、返ってきた成果が正しいかを判断できない。

### FNC-005: 完了の条件と最終確認

タスクを完了にするのは、オーケストレータが成果を最終的に確認し、通ったときだけとすること。

- 最終確認は、成果（変更差分・検証結果）が、タスクの内容（受け入れ基準を含む）と、根拠の設計書・要件定義書に合っているかについて行うこと
- 確認は、オーケストレータ自身が書いた実装の指示に照らさないこと。受け入れ基準と、根拠の設計書・要件定義書に照らすこと
- 確認に通らなかったときは、不足を示して、エラーとして扱い、失敗の状態にすること
- レビューの所見は気づきであり、結果を受け入れるかどうかはオーケストレータが決めること（REQ-013 §1.4）
- タスクグループに属さないタスクは、実装の成功後にレビューし、最終確認に通れば完了にすること
- タスクを完了にしたとき、紐づくタスクが 1 件以上あり、そのすべてが完了した要件も完了にすること。紐づくタスクが 1 件も無い要件は、完了にしないこと

理由: レビューの承認は、所見が無かったことの報告にすぎない。成果が作らせたかったものと合っているかを確認する責任は、任せた側にある。自分が書いた指示に照らして確認すると、指示の解釈が誤っていても通ってしまう。

### FNC-006: タスクグループ

タスクグループの、ビルドが通る単位であることと、途中のメンバーはビルドが通らなくてよいことは、[REQ-024](../../forge/requirements/REQ-024_implementation_plan_spec.md) FNC-008 が定める。そのうえで、次を満たすこと。

- 構成は、ビルドが通る単位であることに加え、実装の意味や目的が共通する範囲でまとめること。意味や目的が共通する範囲でまとめるのは、実装とレビューの効率のためであり、ビルドが通る単位であることを満たしたうえでの、ベストエフォートとする。大きいほど良いのではない。意味や目的が共通しない範囲へ広げると、効率が下がる。効率には、早期検証の効率を含む
- タスクの粒度（REQ-024 FNC-004）は、同じタスクグループの先行メンバーが実装済みであれば満たされる
- メンバーは、実装に成功したとき、実装済みにすること
- 全メンバーが実装済みになってから、タスクグループのレビューを 1 回で行うこと。範囲外の項目から、同じタスクグループの担当分を差し引くこと。精査が浅くなるときは、分けてよい
- 最終確認に通ったとき、全メンバーをまとめて完了にすること

理由: 意味や目的が共通するタスクグループを 1 回でレビューすると、1 つの変更として理解でき、レビューの往復も減る。共通しない範囲へ広げると、不具合の検出が後ろに延び、レビューの対象も散らばる。全メンバーの実装後にレビューするため、先行メンバーを完了にする前に後続メンバーを実装する必要があり、実装済みの状態が要る。

### FNC-007: レビューの依頼と結果の扱い

レビューには、今回の到達目標（REQ-013 FNC-1319）、規範（同 FNC-1320）、並行状態にある文書（[REQ-025](../../forge/requirements/REQ-025_additive_development_spec.md) FNC-003）を渡すこと。

- レビューは、確信のある所見だけを確認なしに修正し、確信の無い所見は利用者へ提示する形で起動すること
- レビューの修正でファイルが変わったとき、検証（ビルド・テスト）を再実行し、成功してから完了にすること
- レビューが承認以外で終わったとき、自動では完了にせず、終わり方と未対応の所見を報告し、次の対処を利用者が決めること

理由: 並行状態の文書を渡さないと、レビューは旧仕様を規範にして所見を出しうる。修正で壊れた状態を完了にしてはならない。レビューの所見は気づきであり、承認以外で終わった結果をどう扱うかは、利用者が決める。

### FNC-008: 計画書の形式と更新

計画書は、次のとおりとすること。

- ファイル名は `{feature}_plan.json` とし、置き場は `.doc_structure.yaml` が文書種別 `plan` として宣言するディレクトリとすること
- 形式は JSON とし、構造は [DES-074](../../forge/design/DES-074_plan_format_design.md) のとおりとすること（5.1）。そこに無いキーとフィールドを持たないこと
- 次を持たないこと。これらは、計画書を作る時点で検出されること
  - 自己依存、存在しないタスクへの依存、依存の循環
  - 設計の識別子が、計画書の設計の対応関係に存在しないタスク（設計に対応しないタスクは、識別子を持たなくてよい）
  - タスクに辿れない要件（要件から、設計を経由して、タスクに辿れないもの。設計が無い、または設計にタスクが 1 件も無い）。実装しない要件は、利用者が要件定義書の側で決める。計画書の作成者は、計画書の中で要件を外さない
- 計画書を書き換えるのは、オーケストレータだけとすること（FNC-002）。書き換えは決定論的な処理が行い、AI が計画書を手で編集しないこと

理由: 機械的に読み取り・更新する文書は JSON とする（REQ-001 FNC-005）。計画書の形が揺れると、タスクの選択と状態の更新が、同じ計画書から異なる結果を生む。依存の構造の誤りは、実行可能なタスクが 0 件になるなど、原因の分からない停止を生む。タスクに辿れない要件は、全タスクが完了しても、その要件が実装されないまま終わる（[REQ-024](../../forge/requirements/REQ-024_implementation_plan_spec.md) FNC-003）。実装するかどうかは要件定義書の決定であり、計画は、決まった要件を実装へ分解するだけだからである。

### FNC-009: 構造化データの受け渡し

タスクコンテキスト（`TaskContext`。5.2）と executor agent の結果（`TaskResult`。5.3）は、定められた型の JSON とすること。

- 構造・置き場・書き込みは、決定論的な処理が担い、AI は内容だけを決めること
- executor agent の結果は、executor が return value として返す応答であり、決定論的な処理が代わりに作れない。受け取る側が 1 か所で検査し、契約に反する結果は、エラーとして扱い、失敗の状態にすること

理由: 決定論的に作れる生成物を AI が組み立てると、受け取る側に検査が要り、検査から落ちたものに気づけない。AI が内容そのものを決める応答だけは、受け取る側で検査するしかない。

### FNC-010: 並列実行

依存せず、互いに待たないタスクは、並列に実行できること（REQ-001 FNC-004）。

- 並列に実行するタスクは、オーケストレータが起動前に、各タスクの内容から、互いに独立であることを確かめること
- 完了したタスクに依存するタスクは、その完了後に実行可能になり、次の選択で選ばれること

理由: 独立でないタスクを並列に実行すると、同じ対象への変更が衝突し、前提が整わないまま実装される。

### FNC-011: executor agent の制約

executor agent は、次を守ること。

- 1 回で 1 つのタスクだけを実装し、範囲外に手を付けないこと
- 計画書を書かないこと。他の Agent を起動しないこと
- 結果は、return value として返す 1 つの経路で渡すこと。手動修正を受け付ける経路は設けない。手で直したいときは、停止の報告を受けて直し、再実行を選ぶこと
- 検証がエラーになったら、修正して再検証すること（1 回）。再検証もエラーになったら、回復できないエラーとして報告すること

理由: 担当範囲を超えた変更と、結果の経路の分岐は、並列に動く executor の成果の衝突と、成果の検査の抜けを生む。

### FNC-012: 実装中の設計書・要件定義書

実装の間、設計書と要件定義書を変更しないこと。誤りと判断したときは、中断し、修正案を示して承認を得ること。

理由: 実装の途中で根拠が変わると、同じ計画書の中で、タスクごとに異なる仕様へ実装される。

### FNC-013: 完了後の流れ

- タスクを完了にするたび（タスクグループは、全メンバーをまとめて完了にしたとき）に、commit の確認フローへ進めること（REQ-001 FNC-006）。並列に実行したタスクは、すべて完了してから、まとめて 1 回進めること
- 未完了のタスクが残るとき、継続を利用者に確認すること
- 全タスクが完了したとき、計画書などを残すか破棄するかを、利用者に確認すること（REQ-024 FNC-006）

理由: 完了のたびにコミットすると、未コミットの変更が、次に実装するタスクの変更だけになる。レビューと最終確認が、対象の変更を、git の状態から特定できる。

## 5. データ形式

値の型は、型名で示す。基本型は、文字列・整数・列挙とする。パスは、プロジェクトルートからの相対パスを表す文字列とし、「パス文字列」と書く。配列は「X の配列」、`null` を許すときは「X または null」と書く。構造を持つ値には型名を付け、使う場所では型名で参照する。

| 型名                 | 意味                                         | 定義           |
| -------------------- | -------------------------------------------- | -------------- |
| `Plan`               | 計画書。`{feature}_plan.json` に JSON で保存 | 5.1（DES-074） |
| `RequirementTrace`   | 要件と設計の対応と、要件の状態               | 5.1（DES-074） |
| `DesignTrace`        | 設計と、要件・タスクの対応                   | 5.1（DES-074） |
| `Task`               | 計画書のタスク 1 件                          | 5.1（DES-074） |
| `TaskContext`        | executor agent に渡す、そのタスク専用の指示  | 5.2            |
| `ScopeOutItem`       | 範囲外の項目 1 件                            | 5.2            |
| `RequiredReading`    | 種別ごとに分けた必読文書                     | 5.2            |
| `VerificationPlan`   | 検証（ビルド・テスト）の要否                 | 5.2            |
| `TaskResult`         | executor agent が返す結果                    | 5.3            |
| `VerificationResult` | 検証（ビルド・テスト）の結果                 | 5.3            |

### 5.1 計画書

`Plan`・`RequirementTrace`・`DesignTrace`・`Task` の構造（キー・フィールド・型・列挙値）は、[DES-074](../../forge/design/DES-074_plan_format_design.md) が定める。進行状態の値の意味は、[REQ-024](../../forge/requirements/REQ-024_implementation_plan_spec.md) FNC-002 が定める。

### 5.2 タスクコンテキスト

`TaskContext` は、executor agent に渡す、そのタスク専用の JSON である。`Task` の全フィールドに、次を加えたものとする（`required_reading` は、型が置き換わる）。他のタスクの情報を含めない。

| フィールド                  | 型                    | 内容                                                                                   |
| --------------------------- | --------------------- | -------------------------------------------------------------------------------------- |
| scope_in                    | 文字列                | 今回到達すべき範囲を 1 行に要約したもの                                                |
| scope_out                   | `ScopeOutItem` の配列 | 範囲外の項目                                                                           |
| required_reading            | `RequiredReading`     | `Task` の `required_reading`（パス文字列の配列）を置き換える。種別ごとに分けた必読文書 |
| implementation_instructions | 文字列                | タスク固有の実装の指示                                                                 |
| verification                | `VerificationPlan`    | 検証の要否。決め方は、この節の末尾に示す                                               |
| spec_authority              | パス文字列の配列      | 並行状態にある文書のパス。該当が無ければ `[]`（REQ-025 FNC-003）                       |

`ScopeOutItem`（各値は単一行）:

| フィールド    | 型     | 内容               |
| ------------- | ------ | ------------------ |
| item          | 文字列 | 項目               |
| owner_task_id | 文字列 | 担当タスク ID      |
| reason        | 文字列 | 分離されている理由 |

`RequiredReading`:

| フィールド       | 型                    | 内容                           |
| ---------------- | --------------------- | ------------------------------ |
| design_docs      | パス文字列の配列      | 設計書                         |
| requirement_docs | パス文字列の配列      | 要件定義書                     |
| strategy_doc     | パス文字列または null | 実装戦略書。無ければ `null`    |
| rule_docs        | パス文字列の配列      | 実装ルール                     |
| reference_code   | パス文字列の配列      | 参照する既存コード             |
| additional       | パス文字列の配列      | 上のどれにも当たらない必読文書 |

`VerificationPlan`:

| フィールド   | 型                | 内容                                           |
| ------------ | ----------------- | ---------------------------------------------- |
| build        | 列挙              | `required` / `skipped`                         |
| build_reason | 文字列または null | `required` のとき `null`。`skipped` のとき理由 |
| tests        | 列挙              | `required` / `optional` / `skipped`            |
| tests_reason | 文字列または null | `required` のとき `null`。それ以外のとき理由   |

`VerificationPlan` の決め方は、次のとおりである。

- `build` は、計画書の `build_check` から決める。`per_task` と `on_group_complete` は `required`、`skip` は `skipped` とする
- `tests` は、オーケストレータが、タスクの内容（受け入れ基準を含む）から決める。`required` でないときは、理由を書く

### 5.3 executor agent の結果

`TaskResult`:

| フィールド     | 型                   | 内容                                                        |
| -------------- | -------------------- | ----------------------------------------------------------- |
| task_id        | 文字列               | 実行したタスク ID                                           |
| status         | 列挙                 | `SUCCESS` / `FAILURE`                                       |
| files_modified | パス文字列の配列     | 作成・変更したファイルのパス。変更なしなら `[]`             |
| summary        | 文字列               | 実装内容の要約（1〜2 行）                                   |
| verification   | `VerificationResult` | 検証の結果                                                  |
| notes          | 文字列の配列         | 推測した軽微な仕様、想定内のエラー、注意事項。無ければ `[]` |
| error          | 文字列または null    | `FAILURE` の直接の原因。`SUCCESS` のとき `null`             |

`VerificationResult`:

| フィールド   | 型                | 内容                                        |
| ------------ | ----------------- | ------------------------------------------- |
| build        | 列挙              | `success` / `skipped` / `failed`            |
| build_reason | 文字列または null | `success` のとき `null`。それ以外のとき理由 |
| tests        | 列挙              | `success` / `skipped` / `failed`            |
| tests_reason | 文字列または null | `success` のとき `null`。それ以外のとき理由 |

`SUCCESS` のとき、`verification` に `failed` を含めないこと。指定された検証が必須のとき、その結果は `success` であること。指定が `skipped` の検証は、`skipped` であること。

## 6. 非機能要件

### NFR-001: 契約に反する結果を成功として扱わない

契約に反する executor agent の結果と、最終確認に通らなかった結果が、成功として扱われないこと。

理由: 成功として扱われた結果は、完了の根拠になる。契約に反する結果が通ると、検査が無いのと同じになる。
