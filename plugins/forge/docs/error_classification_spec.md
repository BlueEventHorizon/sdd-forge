# エラーの定義・分類・原因

## 1. 目的

「失敗したらエラー値を足す」と考えると、値は際限なく増える。増えた値の多くは、受け取る側の振る舞いを変えない。

本文書は、**エラーとは何か、どう分類するか、原因をどう扱うか**を定め、エラーを区別して伝える値を足す基準を示す。対象は、エラーを区別して伝えるあらゆる仕組みである——script の終了コード、agent が返す終了の値、要件定義書のエラーケース節、API の応答コード。値をどう表すかは対象ごとに異なり、本文書は踏み込まない。

## 2. エラーとは何か

**エラーとは、処理が意図した流れで進まなくなる事象である。** 想定していたかどうかは問わない。

ファイルが読めない、指定されたブランチが無い、外部サービスが認証を拒んだ、ネットワークが中断した、プロセスが突然終了した——これらはエラーである。

エラーは**事象**であり、なぜ起きたか（原因。§4）とは別の概念である。

### 2.1 エラーではないもの: 判定できるもの

**失敗に見えて、実は判断の材料であるもの。** 所見が指すファイルが存在しないとき、それは「読めなかった」のではなく「その所見は成立しない」という判定であり、処理は意図した流れで進む。

エラーにすると、判定できるはずのものが処理の中断になる。**まず判定できないかを確かめてから、エラーとして扱うかを決める。**

## 3. 分類

エラーは、回復できるかで分ける。

| 分類                   | 意味                                   | 扱い                                                     |
| ---------------------- | -------------------------------------- | -------------------------------------------------------- |
| 回復可能               | 回復の手段があり、意図した流れに戻せる | 手段を選んで回復する。リトライとは限らない（§3.1）       |
| 回復不能（フェイタル） | 回復の手段が無い、または尽きた         | 停止して報告する。次の判断は、受け取る側（利用者）が行う |

- **分類は固定ではない。** 回復可能なエラーでも、手段が尽きれば、回復不能に移る
- 回復を試みたこと、回復できなかったことは、外へ出す。黙って成功を返したり、空の結果で代えたりしない
- 停止して報告するときは、何が起きたかを自然文で伝える。原因が分かる範囲で添える（§4）

### 3.1 回復の手段

リトライは、回復の手段の 1 つにすぎない。別の経路を使う、待つ、利用者へ確認するなど、手段はエラーごとに異なる。**必ずリトライすればよいわけではない。** 手段が無い、または回復を試みても意図した流れに戻せないなら、回復不能として扱う。

## 4. 原因

**原因とは、エラーがなぜ起きたかである。** エラー（事象）とは別の概念であり、事象から原因が分かるとは限らない。

| 原因               | 例                                                                                                         | 対処する主体     |
| ------------------ | ---------------------------------------------------------------------------------------------------------- | ---------------- |
| バグ               | 実装や配置の誤り。配布物の固定の文書が読めない、内部で組み立てた JSON の形が壊れている、呼ぶ script が無い | 開発者           |
| 障害               | 自分ではどうしようもないもの。プロセスの突然の終了、ファイルシステムの破損、ディスクの枯渇                 | 実行環境の管理者 |
| 利用者の入力・環境 | 存在しないパスの指定、認証の拒否                                                                           | 利用者           |

- **実行中のプログラムが知るのは事象であり、原因は分からないことが多い。** 原因は、分かる範囲で報告に書く。分からなければ、調べる
- **バグは、実行時にあってはならない。** 開発時に直すものであり、実行時に回復を試みない。原因がバグと分かったエラーは、停止して報告する。直すのは開発者である
- **原因ごとに、専用の値や回復経路を作らない。** 受け取る側の振る舞いが変わらないからである。バグに専用の値や回復経路を作ると、バグが運用の一部として扱われ、壊れたまま動き続ける
- 障害への防御実装は、明示的に依頼された場合を除き、範囲外とする。前提が崩れた状況を、局所の対処で救えないためである（[scope_proportionality_spec.md](scope_proportionality_spec.md) §3）

## 5. 値を足すときの問い

エラーを区別する値や分類を 1 つ足す前に、次を確かめる。

- **受け取る側は、この値を見て何を変えるか。** 答えられないなら足さない
- **他の値と畳めないか。** 畳んで振る舞いが変わらないなら、畳んだほうがよい
- **原因ごとの値になっていないか。** 原因は値にしない（§4）
- **判定できないか。** 判定できるなら、それはエラーではない（§2.1）

値で区別しないエラーは、値を持たせず、何が起きたかを自然文で伝える。これは握りつぶすことではない。エラーは必ず外へ出す。伝えないのは**種別**であって、エラーそのものではない。

## 6. 重大度カタログ

| 違反パターン                                                           | 違反時の重大度 | 理由                                                           |
| ---------------------------------------------------------------------- | -------------- | -------------------------------------------------------------- |
| エラーを黙って握りつぶす（成功を返す・空の結果で代える）               | 🔴 critical    | 失われたことが誰にも見えない。最も検出が遅れる                 |
| 原因がバグと分かったエラーに、回復を試みる、または専用の経路を用意した | 🟡 major       | バグが運用の一部として扱われ、壊れたまま動き続ける             |
| 判定できる事象をエラーにした                                           | 🟡 major       | 判定できるはずのものが処理の中断になり、残りの仕事まで止まる   |
| 受け取る側の振る舞いが変わらない値や分類を足した                       | 🟢 minor       | 値が増えるだけで、読み手の負担が上がる                         |
| 障害に専用の値と経路を用意した                                         | 🟢 minor       | 前提が崩れた状況を局所の対処では救えず、対策コストに見合わない |
