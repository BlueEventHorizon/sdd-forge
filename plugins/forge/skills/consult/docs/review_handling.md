# review から委譲されたときの手順

consult が review スキルの本体から、Skill ツールで委譲されたときの扱いを定める。consult の SKILL は用途に依らない対話の方法だけを持ち、review に固有の扱いは本書が持つ。

本書は Read で読まれるため、プレースホルダが置換されない。次の 3 つは、consult の SKILL が置換済みの絶対パスで示す。本書では「SKILL が示すパス」と呼び、パスを組み立てない。

- 記録 script
- 受け渡し本文（要旨）
- 受け渡し本文（推奨案）

## 1. 受け取る評価の扱い

review 本体は、利用者に採否を聞く評価に加えて、次の評価も渡す。

- 確認なしに直す ✅ の評価
- 位置未確定の評価
- ドロップした評価

後者の 3 つは、一覧に載せるが採否を聞かない。**報告のみ**の状態で載せ、結果の列に、どれに当たるかと理由を書く。

**採否を聞く評価が consult topic である。** 各 consult topic について、consult brief（要旨と推奨案）を作る。

進める順は、重要度の高い順とする。重要度は evaluator が付けた値（🔴 critical / 🟡 major / 🟢 minor）をそのまま使う。

## 1.1 提示状態の置き場

提示状態（一覧と各 consult topic の状態・結果）は、会話コンテキストにだけ持つ。状態ファイル・作業ディレクトリ・DB を
持たない。再掲した最新の一覧が、現在の提示状態である。提示状態は永続化されない。会話が終われば失われ、
中断した提示を続きから再開する経路は持たない。続きが必要なら、利用者が同じ対象で新しいレビューを起動する。

## 1.2 実行

決着した内容を、consult は実行しない。実行は review 本体が担う。consult は判断を review 本体へ返して終える（5 節）。

## 2. 表示形式

一覧は、全体の状況を 2 行で示し、すべての項目を横の表で簡略に並べ、いま扱っている consult topic だけを、表にせず箇条書きで詳しく示す。consult brief は、この箇条書きの中で述べる。提示のたびに形式を作らない。`{…}` は値に置き換える。

```markdown
**一覧**（全 {N} 件・採否を聞く {M} 件／決着 {k} 件・残り {r} 件／現在 #{n}）
変更: {前回の一覧から変わったことを 1 行で}

| #   | 論点       | 重要度      | 状態         | 結果                   | 課題                   |
| --- | ---------- | ----------- | ------------ | ---------------------- | ---------------------- |
| 1   | {短い名前} | 🔴 critical | 決着（更新） | {採否と理由}           | —                      |
| ▶ 2 | {短い名前} | 🟡 major    | 進行中       | —                      | {何が解決していないか} |
| 3   | {短い名前} | 🟢 minor    | 未着手       | —                      | —                      |
| 4   | {短い名前} | 🟢 minor    | 報告のみ     | {どれに当たるかと理由} | —                      |

---

**▶ #2　{短い名前}**

- **決めること**: {利用者が決めることを 1 行で}
- **要旨**: {要旨}
- **推奨案**: {推奨案}
- **位置**:
  - `{path}:{行}`
    - 書いてあること: {その行の内容を 1 行で}

---
```

### 2.1 全体の状況（2 行）

- 1 行目は件数と現在位置である。`採否を聞く` は consult topic の件数、`決着` と `残り` は consult topic のうち決着した件数と未判断の件数である。報告のみの項目は、`全` にだけ数える
- 2 行目の `変更` は、前回の一覧から変わったこと（決着・取り下げ・新しく加えた論点など）を 1 行で書く。最初の一覧では書かない

### 2.2 横の表（すべての項目）

- `#` は consult が振る番号である。最初の一覧で、consult topic を重要度の高い順に 1 から振り、そのあとに報告のみの項目を振る。議論の途中で振り直さない。新しく生まれた consult topic は、末尾の番号で加える
- `論点` は、その行だけで何の論点か分かる短い名前である。位置は書かない
- いま扱っている行は、`#` に `▶` を付ける。前回の一覧から変わった行は、状態の後ろに `（更新）` を、新しく加えた行は `（新規）` を付ける。最初の一覧には付けない
- `結果` は決まったこと、`課題` はまだ解決していないことである。1 つの列にまとめない。書くことの無い欄は `—` とする。各欄は 1 句に収める
- 未着手の consult topic の提案は書かない。調べ終える前の提案を並べることになるため。提案は、その consult topic に入ったときに、いまの論点の推奨案として示す

### 2.3 いまの論点（いま扱っている consult topic）

- 表にせず、箇条書きで書く。一覧と見分けられるよう、上下にセパレータライン（`---`）を入れる
- 見出しに `▶ #n` と論点を置く
- `決めること` は、利用者が何を判断するのかを、要旨より先に示す。要旨の代わりにしない
- `要旨` と `推奨案` が consult brief である。10 行程度の目安は、この 2 つを合わせた分量に当てる。他の項目は数えない
- `位置` は原文への到達手段である。**表に入れず、箇条書きで書く**（表の中のパスはクリックして開けない）。リポジトリのルートからのパスと行を `path/to/file.md:行` の形で書き、その下に何が書いてあるかを添える
- AI が 1 つに絞れず選択肢を示すときは、推奨案の中に置く

### 2.4 コンソールの書き方

コンソールは流れて消えるので、後から辿れない。表示形式のほかに、次を守る。

- 並列する項目は表にまとめる。散文で列挙しない
- 章立てを細分化しない。読む量が増え、要点が沈む
- 一覧のほかに表・コード片を並べない。使うなら 1 つまで

## 3. まとめて直す申し出

✅ の評価（指摘が正しく、修正も責任を持って実行できるもの）には、まとめて直す申し出を出す。

- 利用者が承諾したら、その件数を review 本体へ返し、残りを 1 件ずつ進める
- `flawed_premise` の評価は、まとめに含めない

## 4. 記録

consult topic ごとに、consult brief を作り終えたら記録する。次の 3 手で行う。

1. 要旨と推奨案の本文を、Write ツールで、SKILL が示す 2 つのパスへ、そのまま書く
2. SKILL が示す記録 script のパスで、次を実行する
3. 終了コードが 0 でなければ、失敗を利用者へ伝える（終了コード 1 は標準出力の `errors`、終了コード 2 は標準エラーの内容）。既定値で補わない。そのうえで consult brief の提示を続ける

```bash
python3 {記録 script のパス} {評価JSON のパス} {review_id} {round_number} \
  --finding-ids {finding_id}... \
  --summary-file {要旨のパス} --recommendation-file {推奨案のパス}
```

| 引数                                     | 内容                                                                           |
| ---------------------------------------- | ------------------------------------------------------------------------------ |
| `{評価JSON のパス}`                      | review 本体が得た評価JSON の絶対パス。記録の置き場は、このパスの親ディレクトリ |
| `{review_id}` `{round_number}`           | review 本体が会話に持つ値。そのまま渡す                                        |
| `--finding-ids`                          | その評価の `finding_ids`（1 個以上の正の整数）。記録に入れる                   |
| `--summary-file` `--recommendation-file` | 手順 1 で書いた、SKILL が示す 2 つのパス                                       |

- 値は、review 本体が会話に持つものをそのまま使う。組み立て直さない。通し番号は渡さない（script が採る）。AI は記録の JSON を組み立てない
- 終了コードが 0 のとき、標準出力は `{"path": "<記録の絶対パス>"}` である。受け渡し本文の 2 つは script が削除する
- 終了コードが 1 のとき、標準出力は `{"errors": ["<理由>", ...]}` である。記録は残らず、受け渡し本文は残る。直して再実行してよい。直さずに次の consult topic へ進んだときは、残った本文を次の本文で上書きしてよい
- 終了コードが 2 のとき、引数を受理できない。理由は標準エラーに出る。利用者へ伝える
- 評価JSON の中身は読まない。パスは置き場の基準にだけ使う

consult brief の要旨と推奨案には、機密情報の値を書かない。どこにあるか、どの種類かだけを書く。

## 5. 結果の返し方

review 本体へ、次を返す。

| 返すもの       | 内容                                     |
| -------------- | ---------------------------------------- |
| 評価ごとの採否 | 採用する / 採用しない / 保留する、と理由 |
| 決着状況       | 全件決着したか、中断したか、未判断の件数 |

- 全項目が決着していれば、決着した内容（採否と理由）を一覧として返し、全項目が決着した旨を伝える
- 未判断の項目が残っていれば、その件数を未判断のまま残った件数として返す。残った項目と、それまでに決着した内容も返す
