# /forge:start-implement

このスキルは、計画書のタスクを選び、実装を executor agent に任せて、計画書の状態を進めることのみを行う。親が依頼している他の作業を引き継いではならない。自身を Skill ツールで呼ばない。

## Goal

計画書（`{feature}_plan.json`）から選んだタスクを、中断やエラーがあっても状態を失わずに、実装・レビュー・最終確認を経て完了にすること。

## フロー継続

段階が完了したら、立ち止まらず次の段階へ進む。不明点がある場合のみ AskUserQuestion で確認する。

---

## コマンド構文

```
/forge:start-implement [feature] [-n N]
```

| 引数    | 内容                                                                            |
| ------- | ------------------------------------------------------------------------------- |
| feature | Feature 名（省略時は AskUserQuestion で確定する）                               |
| -n      | 優先度順に選ぶタスクの数（省略時は 1 件。依存せず待たないものは並列に実行する） |

引数の解釈は AI が行う。不足・曖昧な引数は AskUserQuestion で補う。

---

## 原則

- **計画書を書き換えるのは、計画書の状態遷移 script だけである。** 計画書を Edit・Write で手編集しない。executor agent は計画書を書かない
- **内容を把握しないまま、executor agent に任せない。** 把握するのは、タスクの説明・受け入れ基準・今回の範囲と範囲外・根拠の設計書と要件定義書である
- **executor agent へ渡すのは、識別値（`plan_path` と `context_id`）だけである。** タスクの中身・指示・必読文書のパスを prompt に書かない
- **script の呼び方は、本文に書いた引数と、標準出力・終了コードの扱いだけに依拠する。** script の内部を読んで同じ処理を自分で行わない。標準出力の `errors` は自然文であり、そのまま利用者へ報告する
- **実装の間、設計書と要件定義書を変更しない。** 誤りと判断したときは、変更せず、エラーの扱いに従う

---

## 計画書の状態遷移 [CRITICAL]

計画書のタスクの状態を変えるときは、次の script だけを使う。

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/update_plan_status.py" \
  --plan-path "{計画書パス}" --to {in_progress|implemented|completed|failed|pending} \
  --task "{task_id}[,{task_id}...]"
```

| `--to`        | 意味                                                                  |
| ------------- | --------------------------------------------------------------------- |
| `in_progress` | 実行中にする                                                          |
| `implemented` | 実装済み                                                              |
| `completed`   | 完了                                                                  |
| `failed`      | 失敗                                                                  |
| `pending`     | 失敗をクリアして未着手に戻す。利用者がそう指示したときだけ使う（1.2） |

- 終了コード 0: 遷移して計画書を書いた。標準出力に更新後の状態（`updated_tasks`）と、`failed` のときに未着手へ戻したタスク（`reverted_task_ids`）、`completed` のときに完了になった要件（`completed_requirement_ids`）が載る。紐づくタスクがすべて完了した要件は、script が完了にする
- 終了コード 1: 遷移は起きていない（計画書は変更されていない）。`errors` を利用者へ報告する。続行しない

**並列に実行しているタスク実行単位からも、本 script は 1 回ずつ直列に呼ぶ。** 同じメッセージで複数の呼び出しを並べない。前の呼び出しの完了（終了コードを得たこと）を待ってから、次を呼ぶ。排他の制御は script が持たないため、並べると互いの更新を取りこぼす。

## Phase 1: 起動と選択

### 1.1 Feature の確定と計画書パスの解決

対象 Feature を確定する。引数があればそれを使い、無ければ AskUserQuestion で確認する。

`${CLAUDE_PLUGIN_ROOT}/skills/doc-structure/SKILL.md` の「出力先ディレクトリの解決」手順に従い、doc_type `plan`、feature `{feature}` でディレクトリを求める。その配下の `{feature}_plan.json` を計画書パス（`{計画書パス}`）とする。エントリが無い場合の扱いは同手順が定める（本スキルは既定パスを持たない）。

### 1.2 起動確認

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/check_startup.py" --plan-path "{計画書パス}"
```

- 終了コード 0: 標準出力の `state` で分岐する
- 終了コード 1: 計画書を読めない・壊れている。`errors` を利用者へ報告して終了する。状態を推測して続行しない

| `state`    | 意味                         | 動作                                                       |
| ---------- | ---------------------------- | ---------------------------------------------------------- |
| `no_plan`  | 計画書が無い                 | `/forge:start-plan {feature}` による作成を案内して終了する |
| `leftover` | 実行中のタスクが残っている   | 下記                                                       |
| `clear`    | 実行中のタスクが残っていない | 1.3 へ                                                     |

`leftover` のときは、`in_progress_task_ids` を示し、AskUserQuestion で「前回の残りか、別の実行が進行中か」を利用者に確認する。前回の残りか別の実行かは、機械的には区別できない。

- **別の実行が進行中**: 計画書を変更せず、起動を中止して終了する（同じ計画書への書き込みが競合するため）
- **前回の残り**: 残っていた実行中のタスクだけを、`--to failed` で 1 回の呼び出しにまとめて失敗にする。実装済みのタスクは残る。`reverted_task_ids` があれば、未着手へ戻したタスクとして利用者に伝える。そのうえで下記の失敗のタスクの確認へ進む（いま失敗にしたタスクも対象に含める）

**失敗のタスクの確認**: `failed_task_ids`（起動確認の出力。前回の残りを失敗にした直後は、そのタスクも足す）が空でないときは、その一覧を利用者に示し、AskUserQuestion で「クリアして再開するタスク」を選んでもらう。失敗のタスクは選択されず、それに依存するタスクも実行可能にならないため、利用者が原因を調べて直したあと、ここで再開を指示する。

- **クリアする**: 選ばれたタスクを `--to pending` で 1 回の呼び出しにまとめて未着手に戻す。失敗にしたときの実装の取り消し（作業ツリーの変更を戻す等）は利用者が行っている前提であり、本スキルは行わない。戻したあと 1.3 へ進む
- **クリアしない**: 計画書を変更せず 1.3 へ進む。失敗のタスクは選ばれない

`failed_task_ids` が空なら、そのまま作業ツリーの確認へ進む。

**作業ツリーの確認**: `git status --porcelain` で、未コミットの変更（未追跡を含む）が無いかを確かめる（読み取りだけ。git の書き込み操作はしない）。レビュー（`--diff`）と最終確認（`git diff`）は未コミットの変更を対象にするため、本スキル以外の変更が混ざると、対象を定められない。

- **変更が無い**: 1.3 へ進む
- **変更がある**: 一覧を利用者に示し、AskUserQuestion で続行するかを確認する。実装済みのまま残るタスクグループのメンバーの変更（1.4）は、ここで見える。続行しないなら、終了する（この確認は計画書を変更しない。ここまでの起動確認で書いた状態は残る）。続行するなら 1.3 へ進む（混ざる変更がレビューの対象に入ることを利用者が受け入れた）

### 1.3 タスク選択

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/select_tasks.py" --plan-path "{計画書パス}" [--count {N}]
```

- `-n N` があれば `--count N` を渡す。無ければ `--count` を省略する（最も優先度の高い 1 件が選ばれる）
- 終了コード 0: 標準出力の `units`（タスク実行単位の配列。実行する順）を得る
- 終了コード 1: `errors` を利用者へ報告して終了する

`units` の各要素は、タスク実行単位である。

| フィールド      | 内容                                                                                                |
| --------------- | --------------------------------------------------------------------------------------------------- |
| `kind`          | `task`（タスクグループに属さないタスク）/ `group`（タスクグループ）                                 |
| `group_key`     | タスクグループのキー。`kind` が `task` のとき `null`                                                |
| `task_ids`      | これから実装するタスクの ID。`group` のとき、依存の順に並んでいる                                   |
| `done_task_ids` | 既に実装済みのまま残るタスクグループのメンバーの ID。実装はしないが、レビューと完了の対象に含まれる |

選ばれるのは、実行可能なタスクだけである（待つタスクは枠を占めず、実行中・実装済み・失敗・完了は選ばれない）。この判定を自分でやり直さない。

- **`units` が空**: 実行可能なタスクが無い事実を利用者に知らせて終了する
- **`units` が空でない**: 選択結果（各タスク実行単位の `kind`・`group_key`・`task_ids`・`done_task_ids`）を、実行の前に利用者へ提示する。承認は求めず、提示したうえでそのまま次へ進む

完了したタスクに依存するタスクは、実行可能になった後の、次の起動の選択で選ばれる。完了を本スキルの中で覚えておく必要は無い。

### 1.4 並列にしてよいタスク実行単位の確認

`units` が 2 つ以上のときだけ行う。並列に実行するのは、**異なるタスク実行単位**である。タスクグループの中のメンバーは、並列にしない。

**実装済みのまま残るメンバーを持つタスクグループ**（選択結果の `done_task_ids` が空でないもの）は、並列の組に入れず、単独で実行する。そのメンバーの変更は、今回の結果として残っておらず、作業ツリーの未コミットの変更としてだけ残っている。他のタスク実行単位の変更が同居すると、レビューの対象を、そのグループの変更だけに定められない。

各タスク実行単位の内容を、計画書の該当タスクを Read して把握する（description・必読文書。計画書は読むだけで、書き換えない）。そこから、各タスク実行単位が変更する対象（ファイル・型・契約）を推定する。

- 対象が重なるもの、または一方が他方の成果を前提とするものは、同じ組に入れず、順に実行する
- 対象を推定できないものも、順に実行する

結果は「並列に実行する組」と「順に実行するもの」に分けて把握し、根拠（対象が重ならない理由）を添えて、組ごとに利用者へ示す。並列の組の中は Phase 3 で同時に起動し、組と組・順に実行するものは、前のものが終わってから進める。

## Phase 2: 準備

タスク実行単位ごとに、その `task_ids` のタスクを 1 件ずつ準備する。`kind` が `group` のときは、`task_ids` の順（依存の順）に、1 件の実装を終えてから次の準備に入る。`done_task_ids` のメンバーは準備しない。

以下の 2.1〜2.7 を、1 つのタスク（`{task_id}`）について行う。

### 2.1 実行中にする

`--to in_progress --task "{task_id}"` で、そのタスクを実行中にする（前述の状態遷移の規則に従う）。実装を始める前に必ず行う。

2.2 以降の準備でエラーが起きたとき（必読文書を読めない・土台の文書が実在しない・文脈作成が拒否した）は、executor agent に任せず、エラーの扱いに従う。実行中にしてから準備に入るため、そのタスクを失敗にできる。

### 2.2 必読文書の収集と補い

土台を script で集める。

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/collect_required_reading.py" \
  --plan-path "{計画書パス}" --task-id "{task_id}" --project-root "${CLAUDE_PROJECT_DIR}"
```

- 終了コード 0: 標準出力の `paths`（重複を除いた土台のパス。計画書の必読文書、設計書、設計に対応する要件定義書）を得る。`problems` が空でないとき（設計書・要件定義書が見つからない・複数見つかる・実在しないパスがある）は、任せる前にエラーとして扱う。省略しない
- 終了コード 1: `errors` に従い、エラーの扱いへ進む

次に、**補い**（既存コードと、タスクに応じた実装ルール）を、AI が探す。

- 実装ルールは、Skill ツールで `/forge:query-db-rules {feature} {タスクのタイトル}` を起動して得る。必要に応じて Skill ツールで `/forge:query-db-specs` も起動する
- 既存コード（類似実装・参照コード）は、Grep・Glob で探す
- 探した手段と語を、会話に残す。探していないことと、該当が無いことを区別するためである。該当が無ければ補いは空でよい。探していないときは、任せる前に探す

土台と補いを合わせたパスの一覧を、以降の「収集したパス」とする。

### 2.3 内容の把握

収集したパスの文書を、**全文**読む（見出しや一部で済ませない。参照コードは、量が多いときは直接関連する部分を優先してよい）。あわせて、計画書の該当タスクを Read し、説明・受け入れ基準・依存を確かめる。

把握するのは、タスクの説明、受け入れ基準、今回の範囲と範囲外、根拠の設計書と要件定義書である。読めない文書があるときは、任せずに、エラーの扱いに従う。把握しないまま次へ進まない。

### 2.4 必読文書の種別分け

収集したパスのすべてを、次の種別のどれか 1 つに入れる。パスを足さず、変えない。

| 種別               | 内容                                     |
| ------------------ | ---------------------------------------- |
| `design_docs`      | 設計書                                   |
| `requirement_docs` | 要件定義書                               |
| `strategy_doc`     | 実装戦略書（パス 1 件。無ければ `null`） |
| `rule_docs`        | 実装ルール                               |
| `reference_code`   | 参照する既存コード                       |
| `additional`       | 上のどれにも分類できないもの。省略しない |

### 2.5 範囲導出

範囲外の候補を script で列挙する。

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/derive_scope.py" --candidates \
  --plan-path "{計画書パス}" --unit "{task_id}"
```

- 終了コード 0: 標準出力の `candidates`（`task_id`・`title`・`description`）を得る。候補が 0 件でもよい
- 終了コード 1: `errors` に従い、エラーの扱いへ進む

`--unit` には、今回準備するタスク 1 件の ID を渡す。同じタスクグループの他メンバーも候補に入る（そのメンバーが担当する項目は、このタスクの範囲外である）。

候補から、次を AI が書く。

- `scope_in`: タスクの description が到達すべき範囲を、**単一行**に要約したもの
- `scope_out`: 範囲外の項目の配列。各要素は `item`（項目）・`owner_task_id`（担当タスク）・`reason`（分離されている理由）。各値は**単一行**とする。理由が候補の説明・戦略書から読み取れないときは「計画上分離」と書き、推測で埋めない。該当が無ければ空配列にする

この導出は、タスクごとに 1 回だけ行う。executor agent に渡す内容と、後続のレビューに渡す内容は、同じものを使う。

### 2.6 実装の指示の作成

2.3 で把握した内容と、2.5 の到達点・範囲外から、タスク固有の実装の指示（1 つの文字列）を書く。到達点・範囲外・受け入れ基準の各項目に触れる。把握した内容から作り、欠けた項目があるときは作り直す。

あわせて、テストの要否（`required` / `optional` / `skipped`）を、タスクの内容から決める。`required` 以外のときは、理由を単一行で書く。ビルドの要否は、計画書の `build_check` から script が決めるため、決めない。

### 2.7 文脈作成

executor agent に渡すタスクコンテキストを、script に作らせる。

1. 候補入力を組み立てる。形は `${CLAUDE_SKILL_DIR}/templates/task_context_input.json` のとおりである（フィールドの集合が一致しなければ拒否される）。`scope_in` / `scope_out` は 2.5、`required_reading` は 2.4、`collected_paths` は収集したパスの一覧（種別分けの検査にだけ使われる）、`implementation_instructions` と `verification.tests` / `verification.tests_reason` は 2.6 の結果を、そのまま置く
2. Write ツールで、`.temp/forge/start-implement/task-context-${CLAUDE_SESSION_ID}-{task_id}.candidate.json` へ書く（シェルコマンドへ埋め込まない）
3. script を 1 回実行する。候補入力のファイルは、成否に関わらず script が削除する

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/build_task_context.py" --create \
  --project-root "${CLAUDE_PROJECT_DIR}" --plan-path "{計画書パス}" \
  --task-id "{task_id}" \
  --input-file ".temp/forge/start-implement/task-context-${CLAUDE_SESSION_ID}-{task_id}.candidate.json"
```

- 終了コード 0: 標準出力の `context_id`（識別値）を得る。値は script が生成したものをそのまま運び、自分で組み立てない。タスクコンテキストは、計画書と同じディレクトリの `tasks/` に置かれる（計画書・実装戦略書と同じライフサイクル。7.2 で一緒に存廃を決める）
- 終了コード 1: タスクコンテキストは作られていない。`errors` を読み、候補入力の形に起因する拒否は、候補を訂正して手順 2 からもう 1 回だけやり直す。2 回目も拒否されたとき、または候補の形に起因しない拒否のときは、エラーの扱いに従う

## Phase 3: 実装

### 3.1 executor agent の起動

Agent ツールで、カスタム Agent `forge:executor`（`${CLAUDE_PLUGIN_ROOT}/agents/executor.md`）を起動する。prompt に書くのは識別値だけである。

```
Agent ツール起動: タスクの実装 (subagent_type: forge:executor)
prompt:
  - plan_path: {計画書パス}
  - context_id: {context_id}
```

必読文書の読み方・実装・検証・結果の形は agent 定義が持つ。**prompt で指示を重ねない。**

並列に実行すると確かめた組（1.4）は、組に含まれる各タスク実行単位について 2.1〜2.7 を済ませてから、**同じメッセージで** executor agent を起動する（状態遷移の呼び出しは、準備の中で 1 回ずつ直列に済ませる）。タスクグループのメンバーは並列にしない。組にタスクグループが含まれるときは、全員の結果を受け取って 3.2 を済ませてから、そのタスクグループの次のメンバーの準備（2.1 から）に入る。

Agent の最終応答（または完了通知）を受け取るまで、その結果に依存する処理へ進まない。完了を `ScheduleWakeup` で待たない。ターンを終えて完了通知を待つ。

### 3.2 結果の受け取り

executor agent の最終応答（return value）を、内容を解釈する前に、結果検査の script へ渡す。return value を heredoc・引用文字列・環境変数としてシェルコマンドへ埋め込まない。

1. Write ツールで、return value **だけ**を、`.temp/forge/start-implement/executor-result-${CLAUDE_SESSION_ID}-{context_id}.consumer.json` へ書く
2. script を 1 回実行する。入力のファイルは、成否に関わらず script が削除する

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/receive_executor_result.py" \
  --project-root "${CLAUDE_PROJECT_DIR}" --plan-path "{計画書パス}" --context-id "{context_id}" \
  --input-file ".temp/forge/start-implement/executor-result-${CLAUDE_SESSION_ID}-{context_id}.consumer.json"
```

- 終了コード 0: 標準出力の JSON が、検査済みの結果である。以降は、元の return value ではなく、この JSON だけを使う。契約に反する結果は、script が `status: FAILURE` の結果へ置き換えて 0 で返す。フィールドの補完・型変換・FAILURE の生成を手作業で行わない
- 終了コード 1: 検査の入口が失敗した（タスクコンテキストを読めない等）。`errors` に従い、エラーの扱いへ進む

検査のあと、結果の成否に関わらず、タスクコンテキストを削除する。

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/build_task_context.py" --delete \
  --project-root "${CLAUDE_PROJECT_DIR}" --plan-path "{計画書パス}" --context-id "{context_id}"
```

検査済みの結果の `status` で分岐する。

| `status` | 動作                                                                                                                                                                                                    |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SUCCESS  | タスクグループのメンバー（`kind` が `group`）は、`--to implemented --task "{task_id}"` で実装済みにする。タスクグループに属さないタスクは、次の段階（レビュー）へ進む。実装済みにしても、完了にはしない |
| FAILURE  | executor agent のエラー、または契約違反である。`error` を添えて、エラーの扱いに従う                                                                                                                     |

`files_modified` と `verification` は、後続の段階（レビュー・最終確認）が使う。結果のフィールドを削除・変換して保持しない。

## Phase 4: レビュー

実装に成功したタスク実行単位を、レビューに出す。レビューを依頼する対象は、次のとおりである。

- **タスクグループに属さないタスク**: 3.2 で SUCCESS になった時点で、4.2 へ進む
- **タスクグループ**: 計画書を Read し、`group_id` のグループキーが `group_key` と同じすべてのタスクが実装済みになったときだけ、4.2 へ進む（計画書は読むだけで、書き換えない）。実装済みでないメンバーがあるときは、レビューへ進まない
  - エラーになったメンバーがあるときは、エラーの扱いに従う
  - 先行が未完了のため今回選ばれなかったメンバーは、未着手のまま残る。その先行が完了した後の起動で選ばれる

並列に実行した組は、組の中のタスク実行単位を 1 つずつ順にレビューする（レビューは作業ツリーを修正し、利用者に確認を求めることがあるため、同時に走らせない）。

### 4.1 到達目標の合成

レビューに渡す到達目標を、script で合成する。

1. 対象のタスク実行単位のメンバーごとに、`scope_in` と `scope_out`（2.5 で導出したもの）を集める。`done_task_ids` のメンバーは、本実行で準備していないため、2.5 と同じ手順（`derive_scope.py --candidates --unit "{メンバーの task_id}"` と、候補からの `scope_in` / `scope_out` の記述）で、メンバーごとに導出して含める
2. Write ツールで、`.temp/forge/start-implement/review-scope-${CLAUDE_SESSION_ID}-{先頭メンバーの task_id}.json` へ、次の形で書く（シェルコマンドへ埋め込まない）。`scope_out` の要素は 2.5 と同じ（`item`・`owner_task_id`・`reason`）である

```json
{
  "members": [
    { "task_id": "{task_id}", "scope_in": "{scope_in}", "scope_out": [] }
  ]
}
```

3. script を 1 回実行する。入力のファイルは、成否に関わらず script が削除する

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/derive_scope.py" --review-text \
  --input-file ".temp/forge/start-implement/review-scope-${CLAUDE_SESSION_ID}-{先頭メンバーの task_id}.json"
```

- 終了コード 0: 標準出力の `review_text` を得る。同じタスク実行単位のメンバーが担当する範囲外の項目は、script が差し引いている。自分で差し引かない
- 終了コード 1: `errors` を読み、入力の形に起因する拒否は、入力を訂正して手順 2 からもう 1 回だけやり直す。2 回目も拒否されたときは、エラーの扱いに従う

`review_text` に、メンバーの受け入れ基準（計画書で `null` でないもの）を、メンバーのタスク ID を添えて足したものを、到達目標（`{到達目標の本文}`）とする。

### 4.2 レビューの依頼

次の 3 つを用意する。

- **規範（ルール）**: 必読文書の種別 `rule_docs` のパス
- **規範（仕様）**: 種別 `design_docs` と `requirement_docs` のパスに、**並行状態にある文書**を足したもの。並行状態にある文書は、次の script で求める。戦略書と `additional` は、並行状態にあるものを除いて渡さない（実装手順の指示であり、規範ではない）
- **対象**: 未コミットの変更（`--diff`）。実装済みのまま残るメンバーを持つタスクグループは、1.4 のとおり単独で実行するため、`--diff` で全メンバーの変更を対象にできる。並列に実行した組のタスク実行単位は、同じ作業ツリーに他のタスク実行単位の変更が同居するため、`--diff` の代わりに、そのタスク実行単位の結果の `files_modified` を `--files`（カンマ区切り）に指定する

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/doc_structure/feature_marker.py" \
  --paths {design_docs・requirement_docs・additional のパス（空白区切り）}
```

- 終了コード 0: 標準出力の `marker_paths` が、並行状態にある文書である（無ければ空）
- 終了コード 1: 判定できない文書がある。`errors` を利用者へ報告し、レビューを依頼せず、エラーの扱いに従う

タスクグループは、メンバー全員の `design_docs` / `requirement_docs` / `additional` / `rule_docs` を合わせ、重複を除く。

`/forge:review` を、Skill ツールで起動する。確信のある所見だけを確認なしに修正し、確信の無い所見は利用者に提示する形（`--auto`）で依頼する。

```
Skill ツール起動: /forge:review
args: --diff --auto --scope "{到達目標の本文}" --project-rules {ルール文書（カンマ区切り）} --project-specs {仕様文書（カンマ区切り）}
```

レビューの実行主体・所見の評価・修正・利用者への提示は、`/forge:review` の定義が持つ。本スキルは、引数と、終了の扱いだけに依拠する。`/forge:review` が終わるまで、次の段階へ進まない。

### 4.3 レビューの終わり方

`/forge:review` の要約報告から、終わり方を判断する。

| 終わり方                                                         | 動作                                                             |
| ---------------------------------------------------------------- | ---------------------------------------------------------------- |
| 承認（対応を要する所見が尽きて終わった）                         | 4.4 へ                                                           |
| 承認以外（未対応の所見を残した完了・失敗・中断など、承認でない） | 自動で完了にしない。4.5 に従い、利用者に報告して次の対処を決める |

承認かどうかが要約報告から判断できないときは、承認以外として扱う。

### 4.4 承認のあと

レビューの要約報告に、レビューが修正したファイルがあるかを確かめる。確かめられないときは、ファイルが変わったものとして扱う。

- **ファイルが変わった**: 検証（ビルド・テスト）を再実行する。要否は、ビルドが計画書の `build_check`（`per_task`・`on_group_complete` は実行、`skip` はスキップ）、テストが 2.6 で決めた要否に従い、`required` のものを実行する。実行したコマンドと終了コードを会話に残す。成功してから Phase 5 へ進む。エラーになったときは、完了にせず、タスク実行単位のすべてのタスクを失敗にするものとして、エラーの扱いに従う。成功と推測しない
- **ファイルが変わっていない**: 検証を再実行せず、Phase 5 へ進む

### 4.5 承認以外で終わったとき

`/forge:review` の終わり方と、未対応の所見を、そのまま利用者に報告する。そのうえで、AskUserQuestion で、次のどれにするかを利用者に決めてもらう。本スキルが決めない。

| 利用者の決定 | 動作                                                                                       |
| ------------ | ------------------------------------------------------------------------------------------ |
| 完了         | 4.4 へ進み、Phase 5 の最終確認を通す。最終確認に通らなければ完了にならない                 |
| 再レビュー   | 4.2 から、もう一度依頼する                                                                 |
| 断念         | タスク実行単位のすべてのタスクを失敗にするものとして、エラーの扱いに従う（状態を残さない） |

## Phase 5: 最終確認

タスクを完了にするのは、オーケストレータが成果を確認し、通ったときだけである。レビューの承認は、確認の代わりにならない。

確認の項目は、タスク実行単位の**各タスク**（タスクグループは全メンバー）について、次から作る。

- そのタスクの受け入れ基準の各項目（`null` なら無い）
- そのタスクの `scope_in` の各項目
- 根拠の設計書・要件定義書のうち、そのタスクに関わる記述

各項目を、成果（変更差分と検証結果）に照らして、`ok` か `gap`（不足）にし、根拠を 1 つずつ書く。

- 変更差分は、git の読み取り（`git status`・`git diff`）と、結果の `files_modified` で確かめる。git の書き込み操作はしない
- 検証結果は、結果の `verification` と、4.4 で再実行したものを使う
- **オーケストレータ自身が書いた実装の指示（2.6）に照らさない。** 指示の解釈が誤っていても通ってしまうためである
- レビューの所見は、気づきとして参照するだけで、合否を決めない

`gap` が 1 つも無ければ合格とする。1 つでもあれば不合格とする。

| 結果   | 動作                                                                                                                                                                                                                                         |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 合格   | `--to completed --task "{task_id}[,{task_id}...]"` で完了にする。タスクグループは、全メンバーを 1 回の呼び出しにまとめる。標準出力の更新後の状態と、完了になった要件（`completed_requirement_ids`）を、利用者へ報告する。そのあと Phase 7 へ |
| 不合格 | 不足を利用者に示し、エラーとして扱い、失敗にする。タスクグループは、不足のあるメンバーだけを失敗にする。エラーの扱いに従う                                                                                                                   |

---

## Phase 6: エラーの扱い [CRITICAL]

次のものは、すべて回復できないエラーとして、この段階に入る。

- executor agent の FAILURE、結果が契約に反する（3.2）
- 準備でのエラー（Phase 2）、状態遷移 script が実行中のタスクを扱えない等の失敗
- 検証の再実行のエラー（4.4）、レビューの断念（4.5）
- 最終確認の不合格（Phase 5）

実行が中断したときは、本段階の処理は走らない。実行中の印が計画書に残り、次の起動の起動確認（1.2）が処理する。

### 6.1 停止して失敗にする

実行をそこで止め、エラーが起きたタスク（Phase 5 の不合格はメンバーのうち不足のあるもの、4.4・4.5 は実行単位のすべてのタスク）を、`--to failed --task "{task_id}[,{task_id}...]"` で失敗にする。

- 終了コード 0: 標準出力の `reverted_task_ids`（失敗にしたタスクに推移的に依存していたため、未着手へ戻した実装済みのタスク）を、利用者に伝える。依存しない実装済みは残る
- 終了コード 1: 遷移は起きていない。`errors` を利用者へ報告して停止する。続行しない

利用者に、失敗にしたタスク、エラーの内容（`error`・`errors`・不足の一覧）、未着手へ戻したタスクを報告する。

### 6.2 設計書・要件定義書の誤り

executor agent の `error`、または自分の確認で、設計書・要件定義書の誤りと判断したときは、**文書を変更しない。** 誤りの内容と修正案を示し、AskUserQuestion で承認を得る。文書の修正は本スキルの外で行われる。

### 6.3 再実行

AskUserQuestion で、再実行するかを利用者に確認する。再実行は、利用者が選んだときだけ行う。

- **再実行を選び、その場の再実行がまだ 1 回も無い**: 失敗にしたタスクと、未着手へ戻したタスクだけを、Phase 2 の 2.1 から再実行する（依存の順）。タスクグループでは、それ以外の実装済みのメンバーは再実行しない。その場の再実行の回数は、タスク実行単位ごとに会話に残す
- **それ以外**（再実行を選ばない、または、その場の再実行が既に 1 回ある）: 停止して報告する。それ以降の再実行は、別の起動で、利用者が失敗をクリアして再開すると指示したときだけ行う（1.2「失敗のタスクの確認」）

## Phase 7: コミットと案内

### 7.1 commit

タスク実行単位を完了にするたびに、commit の確認フローへ進む。並列に実行した組は、組のすべてのタスク実行単位が完了してから、まとめて 1 回進む。失敗にしたタスク実行単位は、進む対象に含めない。

commit の確認フローを担うスキルが available-skills にあるときは、Skill ツールで起動する。無いときは、変更を確認してコミットする手順を利用者に案内する。コミットの内容を本スキルが決めない。

### 7.2 継続と存廃の確認

計画書を Read し、完了でないタスクが残っているかを確かめる（読むだけで、書き換えない）。状態を読めないときは、案内せず、その旨を報告する。

- **未完了のタスクが残る**: 継続するかを、AskUserQuestion で利用者に確認する。継続するときは、1.3 のタスク選択へ戻る
- **すべて完了した**: 計画書・タスクコンテキストの置き場（計画書と同じディレクトリの `tasks/`）・実装戦略書を、残すか破棄するかを、AskUserQuestion で利用者に確認する。3 つは同じライフサイクルであり、個別に確認しない（残すなら 3 つとも残し、破棄するなら 3 つとも破棄する）。自動で削除しない。`tasks/` には、途中で止まった実行の残骸が残っていることがあり、ここで一緒に消える

最後に、タスク実行単位ごとの結果（完了・失敗・未完了）と、その理由を、計画書の状態と一致させて報告する。

### 7.3 差分開発の merge 案内

7.2 で「すべて完了した」ときだけ行う。2.4 で `design_docs` と `requirement_docs` に分類した文書が、差分 feature の一時マーカー（`feature_type: temporary-feature`）を持つかを、次の script で判定する。

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/doc_structure/feature_marker.py" --paths {設計書・要件定義書のパス}...
```

- **終了コード 0 かつ `any_marker` が `true`** → 差分開発である。実装を経て新旧の仕様を 1 つへ統合する段階に入ったため、報告に merge の案内を含める（`${CLAUDE_PLUGIN_ROOT}/docs/additive_development_spec.md` §4。merge は自動で実行しない）
- **終了コード 0 かつ `any_marker` が `false`** → merge の案内は含めない
- **終了コード 1** → JSON の `errors` をそのまま利用者に伝え、merge の要否は利用者の判断に委ねる旨を報告に含める。推測で「差分開発ではない」としない

差分開発と判定したときは、7.2 の報告に続けて次を示す（示すのはユーザー入力のコマンド例であり、本スキルから merge-specs を起動しない）:

```
{feature} は差分開発です。旧仕様は実装期間中に据え置かれているため、新しい仕様と食い違っています。
レビューとテストが済んだら、旧仕様（基本 DIR）へ反映して齟齬を解消してください:
  /forge:merge-specs {基本 DIR} {feature}
```
